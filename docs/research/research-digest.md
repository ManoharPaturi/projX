SUMMARY: State-of-the-art phone-photo OMR in 2026 is still dominated by a classical OpenCV pipeline — document quad detection (Canny + approxPolyDP) or fiducial-marker template matching, 4-point homography (cv2.getPerspectiveTransform + warpPerspective), illumination normalization (min-max normalize, TRUNC thresholds, CLAHE for morphology only), and per-bubble intensity statistics (cv2.mean over the bubble rect) with per-question-strip adaptive thresholds rather than a single global Otsu threshold. The best open-source reference is OMRChecker (MIT, ~90% accuracy on mobile photos vs ~100% on scans, 200 OMRs/min), which registers via multi-scale TM_CCOEFF_NORMED template matching of four corner markers searched per-quadrant, and derives confidence from the largest intensity gap between bubble means plus per-strip standard-deviation outlier gating. Classical CV fails on curved/crumpled pages (needs learned dewarping: DewarpNet, DocTr++, UVDoc, DocRes), glare (L2HRNet/DocHR14K, 2025), and shadowed captures (LP-IOANet, real-time on mobile), and threshold-based fill classification fails on partial fills, faint marks, erasures, and double marks — where a small 3-class CNN (filled/empty/invalid, e.g. Afifi & Hussain arXiv:1711.00972) run via LiteRT on ambiguous bubbles only is the pragmatic mobile solution. For Android, the modern stack is the official org.opencv:opencv AAR (5.0.0.1 on Maven Central, OpenCV 4.14.0/5.0.0 current), CameraX capture with quality gates, and ML Kit Document Scanner (managed flow, no corner access) as an optional capture front-end only.
RECS:
  * Build the primary pipeline in classical OpenCV (it is fast, debuggable, and sufficient for flat sheets), modeled on OMRChecker's proven design: (1) capture -> grayscale -> normalize (cv2.normalize NORM_MINMAX 0-255); (2) locate 4 corner registration markers by per-quadrant multi-scale cv2.matchTemplate with TM_CCOEFF_NORMED (scale search 100%->35%, accept quadrant score >= 0.3, cross-quadrant deviation < 0.41); (3) cv2.getPerspectiveTransform + cv2.warpPerspective onto a fixed processing canvas (adopt OMRChecker's ratios: ~1846x1500 canvas, 40px bubbles, ~59px bubble gap, marker width ~1/17 of sheet width); (4) read bubbles by cv2.mean intensity per bubble rect with a per-question-strip threshold; this gets the ~90%-on-mobile accuracy OMRChecker documents, without any ML.
  * Design the printable sheet around detectability, using measured constants: 4 solid black square fiducials near the corners OUTSIDE the content area (each roughly 1/17 of sheet width, i.e. ~2.5-3x bubble diameter), generous white margin around them for template matching, bubbles >= 20px at capture scale (i.e. >= 0.9mm/px on paper: a 5mm bubble needs ~12MP to fill a 200mm-wide sheet - guide users to frame the sheet filling >= 80% of the frame), round/oval bubbles with aspect ratio 0.9-1.1 tolerance, a bubbled roll-number field as one column per digit, and a QR code for page/student identity (industry-standard per Addmen; SDAPS supports 9999 pages this way). Add a column of timing marks (small black rectangles along one edge, one per question row) as a cheap second registration signal to detect residual vertical stretch after homography.
  * Implement confidence scoring as first-class output, combining OMRChecker's three signals: (a) per-marker template-match score and cross-marker consistency; (b) per-bubble margin = (strip threshold - bubble mean) normalized by strip standard deviation, flagging any bubble with |margin| below a tuned band as ambiguous; (c) per-strip outlier rejection (std-dev gate catching all-black/all-white strips). Route flagged sheets to a human review screen instead of guessing - this converts the ~90% mobile accuracy into ~100% with review of the flagged minority, and directly handles partial fills, double marks, and light pen marks.
  * Add explicit row-level answer semantics: a filled-floor threshold so an empty row returns 'unmarked' rather than argmax (the documented PyImageSearch failure), and 'multi-marked' rejection when two bubbles exceed the floor - both are one-line additions to the countNonZero/mean classifier and are the difference between a demo and a grading product.
  * Handle illumination classically first: per-strip intensity statistics (not global Otsu) absorb uneven lighting by design; apply CLAHE (clipLimit 5.0, tile 8x8) only if needed for morphology/visualization, never before thresholding (OMRChecker's explicit warning); use a 2x10 vertical opening + 5x5 erosion to suppress pen strokes bleeding outside bubble edges and stray marks. Detect glare at capture time (fraction of pixels >= 250 in the sheet region) and prompt for re-capture rather than attempting removal in v1.
  * Add one lightweight ML stage where classical CV measurably fails: a small 3-class CNN (filled / empty / invalid) on 48x48 bubble crops, run via LiteRT (int8) on Android, invoked ONLY for bubbles whose classical margin is ambiguous - Afifi & Hussain (arXiv:1711.00972) show this classifier formulation handles partial, light, and crossed-out marks that defeat thresholds, and a selective-inference design keeps average latency negligible.
  * Plan a dewarping fallback path for curled/crumpled sheets (flat-on-table shots with a homography will silently mislocate grids): start with UVDoc (MIT license, small fully-convolutional grid-based network, DocUNet MS-SSIM 0.785) or DocRes (one model for dewarp + deshadow + binarize, CVPR 2024), converted to .tflite; gate it on a post-homography registration residual check (marker positions deviating from expected grid) so it runs only on the maybe-5% of sheets that need it. Treat dewarp models as research-grade: budget for conversion/validation work, and keep the classical path as default.
  * For handwritten roll-number digits (if any field is handwritten rather than bubbled), use the open-source metric-learning digit models/dataset from arXiv:2504.18948 (built for Indian field forms, CC BY 4.0) instead of training from scratch.
  * Android stack, current as of Aug 2026: OpenCV via Maven Central AAR org.opencv:opencv (5.0.0.1, Apache-2.0; pick the '16kb-page-fix' build for Google Play), CameraX for capture with a quality gate (blur via variance-of-Laplacian, glare via saturated-pixel fraction, quad convexity + all-4-markers-visible before accepting the shot), LiteRT 2.2.0 for the CNN stage. Do NOT rely on ML Kit Document Scanner for capture if you need corner coordinates - it does not expose them.
  * Pilot against ground truth with a labeled corpus of real phone photos under the failure conditions you expect (glare from lamination, ceiling-light shadow bands, crumpled corners, 30-degree skew, faint pencil, pen bleed, double marks), and report per-stage error attribution (marker detection vs warping vs thresholding vs classification) like OMRChecker's accuracy split (~100% scans vs ~90% mobile) - that attribution tells you exactly when each ML fallback pays for itself.
RISKS:
  ! A single global threshold (plain Otsu over the whole warped page) is the most common failure under phone lighting: shadow bands and uneven exposure shift the fill/empty separation regionally. Mitigate with per-question-strip thresholds plus the global largest-gap threshold as fallback - OMRChecker's exact design.
  ! Argmax-over-bubbles without a filled-floor constant silently invents answers for skipped questions, and no multi-mark check accepts double-marked rows as single answers - both documented limitations of the canonical tutorial pipeline; grading software shipping these bugs produces wrong marks with high confidence.
  ! Laminated or glossy sheets and direct flash produce specular highlights that erase bubble content entirely; document highlight removal (L2HRNet/DocHR14K) exists but is a 2025 research model, and general glare removal SOTA (DeVeiler, CVPR 2026) is generative and far too heavy for mobile. Glare must be prevented (matte paper, no lamination, diffuse light) and detected at capture (saturated-pixel gate), not repaired.
  ! 4-point homography cannot fix curl: pages photographed on a desk curve (cylinder-like) so bubble rows bend several millimeters mid-page; grid localization from corner markers alone then drifts. Detect via per-marker/per-timing-mark residual checks; only sheets passing go through the classical path, others go to dewarping or manual review.
  ! Template-matching registration needs its preconditions: markers must be fully inside the frame on a reasonably clean background, and quadrant correlation scores below ~0.3 (or cross-quadrant spread >= 0.41) mean crop failure - OMRChecker hard-fails these. A phone app must therefore enforce 'all four fiducials visible' as a capture-time gate, not discover it at grading time.
  ! Marker-free auto-alignment on generic sheets is a known dead end - OMRChecker removed --autoAlign 'due to low performance on a generic OMR sheet'. Always print explicit fiducials on your own sheets.
  ! CLAHE/edge-enhancement before binarization changes the intensity statistics used for fill decisions (OMRChecker: 'good for morphology, bad for thresholding'); keep enhancement out of the measurement path or re-tune thresholds after it.
  ! Thick pens, marks outside the bubble, second-guess strokes, and erasures are the dominant real-world error sources in deployed systems (SDAPS documents exactly these); a CNN 'invalid' class plus a review queue is more robust than any threshold tweak.
  ! Dewarping/enhancement research models report no mobile latency numbers in their papers (arXiv abstracts for UVDoc, DocTr++, TADoc, Polar-Doc include no ms/MB figures) and ship as PyTorch checkpoints; expect conversion, quantization, and validation effort with uncertain on-device speed until measured on target hardware.
  ! OpenCV 5.0.0 on Android requires the '16kb-page-fix' packaged build for Google Play (16KB page-size requirement) - pinning the wrong AAR variant breaks Play submission; also verify the 4.x->5.x API migration (some API changes in imgproc) before choosing 5.x vs 4.14.
  ! ML Kit Document Scanner solves capture UX but is a closed full-screen flow: no corner coordinates, its own dewarping/cleanup outside your control, and device RAM floor (~1.7GB) - unusable as a component inside a custom pipeline; treat it as an alternative product shape, not a building block.
  ! Minimum-resolution and framing assumptions are easy to violate: below roughly 20px per bubble (or with aggressive JPEG compression) intensity statistics become noisy; enforce capture distance/resolution guidance and validate on the low end (OMRChecker's floor is 640x480 input, which is only adequate for small sheets).
  ! Print variability: xerox/photocopy generations reduce marker contrast and paper brightness; OMRChecker claims robustness to xeroxed sheets, but re-verify your threshold margins against at least 2-3 photocopy generations of your own sheet before rollout.

===== afe5c48a =====
SUMMARY: OMRChecker (MIT, Python/OpenCV, 1.1k stars, actively pushed Aug 2026) is the strongest reference and is directly reusable as an algorithm blueprint, though not as embedded code. Its pipeline is: preProcessors declared in template.json (CropPage / CropOnMarkers / FeatureBasedAlignment / blurs) -> resize to a canonical pageDimensions -> optional morphology-based auto-align -> read per-bubble ROI mean intensity -> a two-tier adaptive "largest-gap" threshold (global page threshold + per-question-strip local threshold) -> mark if darker than strip threshold -> CSV + annotated overlay image. Its template format is the key thing to learn from: a JSON Schema draft 2020-12 document with pageDimensions/bubbleDimensions/preProcessors/fieldBlocks, where each fieldBlock declares origin [x,y] + bubblesGap + labelsGap + direction ("horizontal"/"vertical") + either a fieldType preset (QTYPE_MCQ4/5, QTYPE_INT 0-9 vertical, RTL variants) or explicit bubbleValues/fieldLabels, and the grid is generated purely additively from those four numbers - no per-bubble coordinates are ever stored. Roll numbers work via a QTYPE_INT digit grid joined by customLabels. Its stated performance is 200 sheets/min, ~100% on good scans but only ~90% on mobile images - the central data point for a phone-camera product. Other useful references: LazyOMR (MIT, phone-camera PWA on OpenCV.js, proves on-device viability), AndroidOMRHelper (the OMRChecker author's archived Java/OpenCV Android capture-validation app - exactly the missing mobile half, but unlicensed and stale), SDAPS (the "author the form and the template from one source" model), Aspose.OMR (commercial; human-readable text-markup template generation), Addmen and Verificare (Indian commercial feature benchmarks: sheet designers, Lithocode/QR/ICR zones, manual-correction interfaces, auto-ranking reports, wrong-answer-key detection).
RECS:
  * Adopt OMRChecker's two-tier adaptive 'largest-gap' thresholding rather than any fixed pixel threshold: compute a global threshold across all bubble means on a page, then a per-question-strip local threshold from the largest adjacent gap, and mark a bubble when its mean is darker than the strip threshold. Use OMRChecker's starting constants as your baseline (MIN_JUMP=25, CONFIDENT_SURPLUS=5, MIN_GAP=30, JUMP_DELTA=30, white-page baseline 200 / black-page 100) and re-tune for camera capture. This is the single most valuable algorithmic idea to port - it is what makes detection robust to uneven phone lighting that defeats fixed thresholds.
  * Make the printable PDF and the detection template ONE machine-readable source of truth (the SDAPS/Aspose model). Author the sheet once in a declarative spec, and derive both (a) the print PDF and (b) the detection grid from it. This eliminates the entire class of template-vs-print drift bugs that OMRChecker's manual JSON authoring + iterative --setLayout workflow suffers from. Prefer a human-readable Aspose-style text markup ('?answer_sheet questions=180 options=4 columns=4') layered on top of, or compiled down to, a JSON grid model for the runtime.
  * Use OMRChecker's fieldBlock model for the grid: origin [x,y] + bubblesGap + labelsGap + direction ('horizontal'/'vertical') + fieldType preset + fieldLabels. It is compact, purely additive geometry, trivially validated, and proven across the many community templates. Add: explicit named FIELD_TYPE presets for your needs (MCQ4/MCQ5, INT 0-9 vertical digit grid for the roll number, RTL variants), per-block bubbleDimensions and emptyValue overrides, and range-expanded field labels ('q1..180').
  * Define template coordinates in a canonical normalized space (OMRChecker resizes every image to template pageDimensions before reading; community templates range from 299x398 to 1846x1500, proving the space is arbitrary and self-relative). Better: author in real print units (mm at target DPI) and compile to a canonical detection space, so PDF generation and detection can never disagree. Validate with JSON Schema draft 2020-12 and additionalProperties:false exactly as OMRChecker does - it catches template typos at load time.
  * For registration, use four registration markers found by quadrant-restricted template matching (OMRChecker's CropOnMarkers) as your primary anchor: scale sweep 35-100% in 10 steps with TM_CCOEFF_NORMED, split the image into quadrants with separator lines so a match cannot straddle a midline, reject a quadrant below match score 0.3 or when its score deviates from the global best by >=0.41, then four_point_transform on the ORIGINAL (unprocessed) image using the four centers. Size markers at roughly 1/17 of sheet width. This is far more robust on skewed phone photos than whole-page contour finding.
  * Add L-shaped corner markers as a second, redundant anchor type from day one. OMRChecker issue #270 (maintainer-filed, 'good first issue') notes many real OMR sheets use L-shaped corners and that supporting them would 'increase accuracy and success rate'. Since you control the sheet design, print both markers and L-corners and let detection prefer whichever resolves with higher confidence - a cheap form of redundancy for glare/occlusion.
  * Put an identification code ON the sheet and read it: a QR code (as SDAPS does for multipage identification) encoding sheet-type ID + template version + optionally an exam ID, plus the bubbled roll-number digit grid (OMRChecker's QTYPE_INT vertical 0-9 grid with customLabels joining digits into one output column). The QR removes all ambiguity about which template to apply and enables multi-page and multi-variant sheets (correctAE's 6-variant equivalence-table feature is the coaching-institute pattern to copy).
  * Emit an explicit numeric confidence per bubble, per question and per sheet. OMRChecker has no such score (confidence is implicit in gap magnitude and strip-std tests, and the low-confidence code path is literally a TODO 'pass'). Compute confidence from the gap magnitude relative to MIN_JUMP + CONFIDENT_SURPLUS, the strip std vs global std, and the margin between the top and second-brightest bubble. This is what lets a mobile app decide 'accept' vs 'ask the invigilator to re-shoot' vs 'flag for manual review' - the workflow Addmen and Verificare both ship as a 'manual correction interface'.
  * Port the detection core to Kotlin/C++ with OpenCV for Android (current 4.x; note AndroidOMRHelper bundled OpenCV 3.1.0 and its author says it 'needs a huge upgrade'). LazyOMR proves on-device OpenCV is viable even in OpenCV.js at ~3.4MB; native OpenCV will handle 200 questions comfortably. You only need to port core.py's thresholding plus the processors - deliberately skip OMRChecker's pandas, matplotlib, rich, screeninfo, deepmerge and PyMuPDF dependencies, which are reporting/CLI-only and useless on Android.
  * Build capture-time validation as a first-class gate (the AndroidOMRHelper concept, which is exactly why OMRChecker's author wrote it): live camera edge overlay to frame the sheet, plus pre-flight checks for blur, glare/overexposure, low contrast, and all four markers visible. Given OMRChecker's own numbers - near 100% on good scans vs ~90% on mobile images - rejecting bad captures at the camera is worth more accuracy than any detection algorithm improvement. Target a capture resolution comfortably above OMRChecker's 640x480 floor; for a 180-question A4 sheet aim for enough pixels that a bubble spans roughly 20px or more (OMRChecker sample1 uses 40x40px bubbles in canonical space).
  * Steal the specific pre-processing insight from OMRChecker core.py: apply CLAHE only to a morphological/analysis copy and never to the copy you threshold (their comment: 'clahe is good for morphology, bad for thresholding'), and maintain separate morphological thresholds for camera (60) vs scanned (40) input. Also handle the xeroxed-sheet case, where the global threshold collapses to 255 and everything reads as dark.
  * Design the grading/evaluation format up front along OMRChecker's evaluation.json lines but more simply: per-question answer (single, multi-correct array, or weighted), and a marking scheme that must explicitly define correct/incorrect/unmarked scores, supporting negative marking (-1) and fractional partial marking (1/4) - the JEE/NEET requirement. Add per-subject/section marking schemes and post-hoc question cancellation with automatic recalculation (correctAE), plus statistical 'wrong answer key detection' (Verificare) that flags questions where a large majority chose the same non-key answer.
  * Benchmark against the right numbers: OMRChecker's 200 sheets/min on desktop is your reference for native on-device speed (expect slower but adequate - one sheet per photo, not batch); its ~90% mobile accuracy is the number to beat; RescueOMR's ~2% needing manual review across 10,000 documents is a realistic target for a well-designed sheet plus capture validation. LazyOMR's self-assessment ('not suitable for high-stakes exams') marks the quality bar you must clear for Indian coaching-institute use.
RISKS:
  ! License traps: OpenMCR's code is GPL-3.0 AND its answer sheet artwork is CC BY-NC-SA 4.0 (non-commercial) - do not borrow its sheet layout. RescueOMR is AGPLv3 (network-copyleft). AndroidOMRHelper has no visible license file, so default copyright applies and its code must not be reused without permission; it is archived anyway. Only OMRChecker (MIT) and LazyOMR (MIT, with an attribution note) are safely borrowable - and only for reference/algorithms, since neither runs on Android.
  ! Mobile image accuracy is the known hard problem, confirmed by every source: OMRChecker drops from near 100% on scans to ~90% on phone images, and LazyOMR explicitly disclaims high-stakes suitability citing lighting, shadows, glare, low-contrast bubbles, smudges and creases. A 90% accuracy rate is roughly 10-20 wrong readings per 180-question sheet - unusable without a human-review pass. Budget for the review UI, not just the detector.
  ! Whole-page contour registration (the PyImageSearch approach most GitHub repos copy) is fragile on phones: it requires the sheet to be the dominant object with all four corners visible and correctly guesses 4-vertex contours. Prefer marker-based registration. Note also OMRChecker dropped --autoAlign as a default 'due to low performance on a generic OMR sheet'.
  ! OMRChecker's registration has hard failure modes worth knowing: it exits with code 31 if the marker image file is missing, returns None if ANY of the four quadrant matches scores below 0.3 or deviates 0.41 from the best, and warns 'Template matching too low!' below threshold. A single occluded or glaring marker rejects the whole sheet. Your design should degrade gracefully (retry with the alternate anchor type, or flag the specific corner) rather than fail.
  ! Detection-vs-anatomy edge cases to design for explicitly, gathered from the sources: blank answers (PyImageSearch misses them entirely - need a minimum-fill threshold per row), multiple marks per question (OMRChecker concatenates and flags; you must decide invalidate vs partial credit), all-black and all-white strips (OMRChecker gates via strip std vs global std), xeroxed/photocopied sheets where global threshold collapses to 255, and faded or partially-filled bubbles.
  ! Template setup difficulty is the recurring user complaint across open-source OMR: OMRChecker requires hand-authoring JSON and iterating with --setLayout; SDAPS requires LaTeX; Aspose requires learning a markup language. If your template authoring is not substantially easier, adoption will stall. Since you generate both sheet and template, most of this friction disappears - but only if you never allow the two to be edited independently.
  ! No open-source project provides a production-grade on-device Android OMR pipeline. AndroidOMRHelper is the only Android OMR app found and it is a 3-commit archived WIP on OpenCV 3.1.0; LazyOMR is a browser PWA capped at 50 questions and A4. You are effectively building the Android detection core from scratch, porting algorithms rather than code.
  ! Commercial accuracy claims are marketing: Addmen ('100% accuracy', '1000s of sheets') and Verificare ('100% accuracy', '300 sheets/min') publish no methodology. Do not calibrate your targets to them; calibrate to OMRChecker's honest 90%-mobile figure and RescueOMR's 2% review rate.
  ! Sheet-design decisions constrain detection permanently. OpenMCR is locked to two hardcoded sheets; LazyOMR is A4-only and max 50 questions by construction. Decide paper size, question count range (50-200), option count (4 vs 5), column layout and roll-number width up front and validate that your bubble size in captured pixels stays viable at the worst-case capture distance - OMRChecker uses 40x40px bubbles in canonical space with 640x480 as the absolute floor.
  ! Detection of a bubbled roll-number field has a distinct failure mode: an illegible or multi-marked digit grid silently mis-attributes a student's sheet. Add a checksum digit to the roll number, or validate the read roll against an expected roster, and route any roll-grid anomaly to mandatory human confirmation rather than auto-accepting.

Data model: `question_set (code, exam_id)` + `set_question_map (set_code, sheet_question_ordinal → canonical question_id)`, so shuffled sets map onto one canonical question bank and analytics aggregate correctly. Flag at read time: blank set code, multiple-marked set code, or a set code with no key loaded.
  * ADD A WRONG-KEY DETECTOR as a cheap post-grade heuristic. Verificare ships this as an AI feature; you can approximate it well: after a grading run, surface any question with (i) near-zero correct-rate across the whole cohort, or (ii) a correct-rate that collapses relative to its difficulty index, or (iii) an unusually high multi-mark rate. Addmen's advanced module already computes 'difficulty index, discrimination index, candidate response distribution, distractor analysis' per question — compute these from your own per-bubble table and use them as the outlier signal.
  * RETAIN THE ORIGINAL SHEET IMAGE AND BUBBLE CROPS. Both Addmen and Remark surface the original image inside every correction dialog ('it also shows the image of the original sheet to make it easy to compare'). On mobile this is cheap and it is the difference between a teacher trusting a re-grade and arguing with it. Store sheet-level image + per-question crop refs alongside the raw read row; keep the layout/geometry version used at read time so crops can be regenerated.
  * SUPPORT 'N-OF-M' SECTIONS. Model `section.max_counted` (questions counted = first N valid responses in serial order, extras ignored with no penalty) — this is NEET/JEE Main Section II behaviour and Addmen's documented 'answer 10 out of 15' logic. Without it you will mis-grade any NEET-pattern test where a student fills 6 of 5 required.
  * DESIGN THE INTEGER GRID WITH RIGHT-ALIGNED DIGITS AND EXPLICIT LEADING-ZERO SEMANTICS. Two digit columns (00–99) covers JEE Main (answers 'rounded off to the nearest integer') and most JEE Advanced integer items; make column count per-question configurable in the layout ('one-digit, two-digit or more digit blocks'). Resolve '03' vs '3' at the mapping layer as Addmen warns. Reuse the same digit-column widget and reader for the roll-number field, and apply Addmen's rule that blank columns are ignored but a filled '0' is a value — then validate the roll number against the enrolled ID list and flag 'Blank ID, Duplicate ID, Invalid Length, Invalid ID not in list, Multiple marked column'.
  * BUILD A 4-TYPE QUESTION CATALOGUE, NOT 1. (1) SINGLE_CORRECT, 4 options; (2) MULTI_CORRECT, 4 options, N-valid; (3) INTEGER_DIGITS, k columns × 10 digits; (4) MATRIX, r rows × c columns (one mark per row, partial or all-or-nothing scoring). Also allow a MATCH_LIST_REDUCTION type (list-match collapsed to an ordinary 4-option single-correct item, as JEE Advanced 2026 actually does) so one sheet can mix all of them — Addmen's IIT-pattern sheets do exactly this.
  * DESIGN BUBBLE GEOMETRY FOR DETECTION FIRST: ~40–50 px equivalent bubble (≈4.5–5.5 mm at 300 dpi), thin outlines, light/small option labels so they can never be thresholded as marks, and strict minimum inter-bubble gaps ('bubbles touching each others are defective sheets'). Print the bubble outline in a dropped-out colour or keep it very light if you ever scan in greyscale, since large dark labels 'could be falsely detected as filled marks on black-and-white sheets'. Target ≥150 dpi capture (Addmen: 100 dpi floor for OMR, 150 dpi for barcode/ICR) and design registration/timing marks to tolerate the skew your auto-alignment step corrects.
  * IMPLEMENT THREE READING MODES mirroring Addmen — Auto (skip and quarantine with a filename prefix), Alert (prompt per exception at read time), Manual (stop on every sheet) — plus a post-read editor that sorts by issue type and shows the sheet image. On a phone this maps to: background capture queue → exception inbox → per-sheet tap-through review, which is far better UX than blocking the camera on each ambiguous sheet.
  * VERSION EVERYTHING THAT AFFECTS A SCORE. Each `scoring_run` row records (answer_key_version_id, scoring_rule_snapshot, sheet_layout_version, threshold_param_set_id). This gives you a free audit trail, lets you reproduce any historical marksheet exactly, and makes the 'curve a test / throw out questions / change correct answers and regrade' workflow a safe insert rather than a destructive update. Addmen gates editing behind passwords and logs data-editing activity to SQL in its professional edition — do the same from day one.
RISKS:
  ! The current design assumption is provably wrong for the target market. JEE Advanced pattern multi-correct questions score N filled bubbles as a legitimate partial-credit answer (+3/+2/+1). If the classifier rejects any multi-mark as an invalid 'double mark', the system cannot grade the most distinctive JEE-pattern question type at all and will silently zero-out correct multi-selects.
  ! Marking schemes are not stable year to year — the multi-correct penalty moved from −2 to −1 and JEE Main's numerical section gained −1 negative marking in 2026. Any marking constant baked into the grading engine is a latent bug that surfaces the first time a coaching institute runs a new year's pattern.
  ! Scoring rules vary by SECTION within a single paper (JEE Advanced 2026 Paper 1: +3/−1 in S1, +4 partial/−1 in S2, +4/no-negative in S3, +4/−1 in S4; Paper 2 S4 is only +2). A single exam-level marking scheme will mis-grade most real JEE-pattern papers.
  ! Do not trust third-party exam-pattern summaries. eSaral's 2026 JEE Advanced section table contradicts the official jeeadv.ac.in PDF on Paper 2's section composition, and major JEE Main sources disagreed on whether numerical questions carry −1 until the official bulletin settled it. Always derive scoring presets from the primary bulletin/paper.
  ! 'Multi-mark = wrong' is not the same as 'multi-mark = invalid' and not the same as 'multi-mark = zero'. NEET treats it as incorrect (−1); JEE Advanced single-correct says '−1 In all other cases'; some institutes award 0. Making this a per-question-type configurable action (multi_mark_action) rather than a global rule avoids a wrong default that cannot be fixed without re-grading.
  ! Erasures, whiteners and stray marks are the dominant real-world noise source and they read as data, not as absence: 'even very light pencil remains might be detected by OMR software as stray marks', and smudges 'may cause the software to detect double-mark or invalid responses'. A pure black/white classifier will mis-read a large fraction of real coaching batches. Budget for a PROBABLE band and a human-confirmation step from the start.
  ! If you persist only computed scores you lose re-grading entirely. NTA's own correction path (dropped question → +4 to all candidates) requires retroactive re-evaluation of the whole cohort. Store raw per-bubble reads plus images; otherwise an answer-key fix means re-photographing thousands of sheets.
  ! The 'first N in serial order' rule for n-of-m sections is easy to get wrong: extras are ignored without penalty, but which N count is determined by sheet order, so any reordering or off-by-one in question numbering shifts marks silently.
  ! '03' vs '3' and blank-column-vs-zero in integer/roll-number grids are a classic silent corruption. Ambiguity must be resolved at a single well-tested mapping layer, and a blank leading digit column must be flagged rather than assumed zero.
  ! A wrong or missing set-code read silently grades a student against the wrong key — the most damaging failure mode because the output looks plausible. Detect it structurally (blank/multi-marked set code, set code with no key loaded, per-question correct-rate anomalies) rather than trusting the read.
  ! Distinguishing an intentional multi-select from two half-filled bubbles is genuinely ambiguous at low image quality. Without per-bubble fill ratios retained, you cannot revisit the decision later; with them, you can re-threshold the whole batch offline.
  ! Small dark option labels and thick bubble outlines can themselves be thresholded as filled marks, especially on greyscale/photocopied sheets. Sheet design and the classifier must be co-designed, and the layout must be versioned so a geometry change invalidates old reads deterministically rather than producing mystery misreads.
  ! JEE Advanced and JEE Main are now CBT; the printed-OMR market you are serving is coaching institutes replicating those patterns. Validate requirements against institute practice (Addmen/Verificare feature sets), not against NTA's current exam-delivery mechanics.
