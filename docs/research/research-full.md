SUMMARY: As of August 2026, all three paths are viable for on-device OMR, but they differ sharply in cross-platform robustness. (a) Flutter: opencv_dart (v2.2.2, wraps OpenCV 4.x via dart:ffi with Native Assets, prebuilt Android+iOS binaries, Apache-2.0) is the only maintained OpenCV binding — opencv_4 is 5 years stale; camera 0.12.0+2 (CameraX-backed) or camerawesome 2.5.0 handle capture; pdf 3.13.0 generates the OMR sheet PDF in pure Dart identically on both platforms. (b) Native Kotlin: OpenCV Android SDK ships as a Maven Central AAR (org.opencv:opencv 5.0.0.1 / 4.14.0), CameraX 1.6.2 is stable and Compose-native; ML Kit Document Scanner is Android-only, Google-Play-Services-dependent, launches a fixed Google full-screen UI, exposes no polygon/corner API and outputs only JPEG/PDF — it cannot replace custom edge detection for a controlled OMR pipeline (no programmatic capture, ML "cleaning" can alter bubble pixels), though its dewarped JPEG could serve as an optional import path. (c) If ML is needed for mark classification or dewarping, ONNX Runtime (onnxruntime-android 1.22.0 on Maven Central; "onnxruntime-mobile" is superseded by custom minimal builds per current docs) or LiteRT (ex-TensorFlow Lite, renamed Sept 2024) both work, with a stale third-party Flutter FFI package (onnxruntime 1.4.1, ~2 years old) as the weak link. Recommendation: Flutter as the single codebase (app + CV pipeline + PDF generation), using opencv_dart 2.2.2 + camera 0.12.0+2/camerawesome 2.5.0 + pdf 3.13.0, with a native-Kotlin fallback (OpenCV 4.14.0 + CameraX 1.6.2 + ONNX Runtime 1.22.0) if capture-loop performance on low-end devices demands it. Classical OpenCV (adaptive threshold + contour/registration-mark detection + perspective warp), not ML, should remain the primary detection algorithm; OMRChecker (Python/OpenCV, MIT) proves the template-driven classical pipeline at scale but reports only ~90% accuracy on mobile photos vs ~100% on scans, so capture UX and dewarping quality are the real risk, not classification.
 - Flutter OpenCV bindings — opencv_dart 2.2.2 (pub.dev, publisher rainyl.dev, Apache-2.0, published ~mid-Aug 2026): wraps OpenCV 4.x via dart:ffi using Dart's Native Assets mechanism; requires Flutter >= 3.38 / Dart >= 3.10. Ships prebuilt binaries for Android (armeabi-v7a, arm64-v8a, x86_64) and iOS (arm64 + x86_64/arm64 simulator) — no runtime download. Default build includes only core, imgproc, imgcodecs; other modules (calib3d, dnn, features2d, objdetect, aruco, ximgproc) are bound and tested but must be enabled via pubspec hooks config (include_modules) or they throw symbol-not-found. ~7.17k weekly downloads, 140 pub points. Repo explicitly says 'WIP, APIs may change'; documentation still on TODO list; single primary maintainer.
 - opencv_4 (pub.dev) is effectively dead: version 1.0.0 published ~5 years ago, wraps OpenCV 4.3.0 (2020), unverified publisher, license listed unknown, ~73 weekly downloads. Do not use. Custom hand-rolled FFI against OpenCV is unnecessary given opencv_dart exists — writing your own bindings for calib3d/imgproc is weeks of work with symbol-loading pitfalls on both ABIs.
 - Flutter camera plugins: camera 0.12.0+2 (flutter.dev first-party, BSD-3, ~551k weekly downloads, 160 pub points; Android minSdk 24, iOS 13+; endorsed Android implementation camera_android_camerax 0.7.x is built on CameraX) supports startImageStream for per-frame analysis in Dart, but YUV->RGBA conversion happens in Dart/native bridge and the plugin does not manage lifecycle since v0.5.0. camerawesome 2.5.0 (apparence.io, MIT, ~24.4k weekly downloads) offers a purpose-built image-analysis stream with configurable maxFramesPerSecond (~20 fps) delivering nv21 (Android)/bgra8888 (iOS) planes plus torch, tap-to-focus, exposure and zoom controls — well suited to a guided document-capture screen; last published ~14 months before Aug 2026, so release cadence is slow but the package is stable.
 - Flutter on-device PDF generation: pdf 3.13.0 (publisher nfet.net, Apache-2.0, published ~2 months before Aug 2026) generates PDFs entirely in Dart — identical output on Android and iOS. Supports custom page sizes (PdfPageFormat), mm/cm/inch unit constants (1.0 unit = 1/72 inch, PdfPageFormat.mm conversions), TTF font embedding (pw.Font.ttf), vector graphics (circles/lines for bubbles and timing marks), pw.MultiPage for automatic pagination of marks sheets; companion printing package handles OS print/share dialogs. This matters for OMR: the printable sheet layout must be geometrically identical regardless of which phone/platform generates it, and a pure-Dart generator guarantees that.
 - Native Kotlin OpenCV: OpenCV Android SDK is published to Maven Central as an AAR at org.opencv:opencv (Maven Central shows latest 5.0.0.1, published ~June-July 2026). Upstream releases: OpenCV 5.0.0 (06 Jun 2026, marked Latest on GitHub; release notes specifically call out an Android 16 KB-page NDK fix and a 4.x->5.x migration guide) and OpenCV 4.14.0 (19 Jul 2026). Maven publication started at 4.9.0 (Dec 2023), so 4.10-4.14.x are all available as Gradle dependencies with Java/Kotlin bindings via OpenCVLoader. Staying on 4.14.x is the conservative choice; 5.x is a major-version break weeks old at research time.
 - Native Kotlin camera: CameraX stable line is 1.6.2 (androidx.camera:camera-core/camera2/lifecycle/view/compose/effects, released 26 Aug 2026; next alpha 1.7.0-alpha03). CameraX 1.5.0 (10 Sep 2025) raised default minSdk from API 21 to API 23; 1.6.0 migrated to CameraPipe, the same high-performance stack as the Pixel camera app, and carries a fix recommended for Android 17 compatibility (Google issue 519796838: update to >= 1.5.2/1.6.0 to avoid crashes). camera-compose is stable, enabling Compose-native camera UI. ImageAnalysis use case delivers YUV_420_888 frames at a resolution you select, feeding OpenCV Mat conversion directly.
 - Google ML Kit Document Scanner API: Android-only (the ML Kit docs navigation shows only an Android entry for doc scanner; no iOS equivalent), API level 21+, and requires Google Play Services — the entire UI flow, ML models and large resources are delivered dynamically by Play Services (~300 KB app footprint, no camera permission needed). Developer control is limited to: max page count, gallery import on/off, and one of three scanner modes (SCANNER_MODE_BASE = crop/rotate/reorder, BASE_WITH_FILTER = adds filters, FULL (default) = adds ML cleanup that erases stains/fingers, and auto-adds new features via Play Services updates). Output is JPEG and/or PDF files. It does NOT expose the detected document polygon/corners, detection confidence, or any programmatic capture — there is no API-only mode; it always launches Google's full-screen activity (GitHub issue googlesamples/mlkit#1026 reports forced fixed orientation on its activity). Verdict for OMR: it can dewarp a page, but it cannot replace custom edge detection for a controlled OMR pipeline — no quad API, no automation, FULL mode's ML cleanup can alter bubble-fill pixels, JPEG re-encode loses fidelity, GMS dependency fails on non-GMS devices, and zero iOS parity means a second implementation later. At most, use it as an optional gallery-import convenience path.
 - ML runtimes: TensorFlow Lite was renamed LiteRT in September 2024 (developers.google.com/edge/litert); runtime, APIs and .tflite format unchanged; TensorFlow 2.20.0 deprecates tf.lite in favor of the dedicated LiteRT SDK. ONNX Runtime Mobile: the current ONNX Runtime install docs (onnxruntime.ai/docs/install) no longer list an onnxruntime-mobile artifact — the size-reduction path is now the regular onnxruntime-android package plus a custom minimal build containing only your model's opsets; XNNPACK and NNAPI execution providers are documented separately. Maven Central index shows com.microsoft.onnxruntime:onnxruntime-android latest 1.22.0 (May 2025; newer 1.2x releases may exist past the index snapshot). iOS via CocoaPods onnxruntime-c / onnxruntime-objc. Flutter FFI bindings exist (pub package onnxruntime 1.4.1 by gtbluesky/onnxruntime_flutter, Android API 21+, arm32/arm64, iOS/macOS, isolate support) but were published ~2 years before Aug 2026 — verify against your ONNX opset before relying on it, or wire onnxruntime-android natively via a thin platform channel.
 - A small CNN for bubble-mark classification (e.g., 28x28 or 48x48 ROI -> filled/empty/unmarked) or a dewarping model is comfortably in LiteRT/ONNX Runtime Mobile territory (<1-5 MB int8 model, <10 ms/frame). But classical OpenCV (adaptive threshold + contour area/intensity statistics on registered ROIs) is the proven default for bubble reading; prior art OMRChecker (github.com/Udayraj123/OMRChecker, Python/OpenCV 4, MIT license, used at scale by Technothlon/IIT Guwahati) reports nearly 100% accuracy on good scans but only ~90% on mobile photos — indicating the phone-capture/dewarp stage, not bubble classification, is the accuracy bottleneck, and a template.json-driven layout approach with angle-agnostic alignment works at 200+ sheets/minute.
 - Android 16 KB memory-page compliance: Google Play requires all apps targeting Android 15 (API 35)+ to support 16 KB page sizes on 64-bit devices; from 1 Feb 2027 updates that don't support 16 KB cannot be released (developer.android.com/guide/practices/page-sizes). Any native-lib path (OpenCV AAR, opencv_dart prebuilt .so, ONNX Runtime, LiteRT) must be verified with zipalign -c -P 16 and NDK r28+; OpenCV 5.0.0's Android packaging specifically fixed 16 KB alignment, and recent ONNX Runtime/LiteRT builds support it. Check opencv_dart's shipped binaries early in the project.
 - Platform-availability summary for the iOS port: opencv_dart, camera, camerawesome, pdf, onnxruntime-flutter all ship iOS implementations today; CameraX/ML Kit/LiteRT-as-shipped are Android-side only (LiteRT does have an iOS runtime, but the Google Play-services delivery variant does not); OpenCV itself has first-party iOS support via CocoaPods, so a native-Kotlin start means re-implementing capture (AVFoundation) and PDF generation separately on iOS.

===== RESEARCH (agent a723183e) =====
SUMMARY: For an offline-first mobile OMR grading app, the strongest 2026 stack for report generation is: Flutter `pdf` (v3.13.0) + `printing` (v5.15.0) for on-device per-student marksheets and auto-paginated consolidated class sheets (Android-native alternative: `android.graphics.pdf.PdfDocument` + Canvas for silent generation, since the WebView/PrintManager route always shows the system print dialog); `excel_plus` (v2.16.0, an API-compatible actively-maintained fork of the stale `excel` 4.0.6) or `syncfusion_flutter_xlsio` (v34.2.5) for XLSX, and the `csv` package (v8.0.0, RFC 4180 with UTF-8-BOM Excel mode) for CSV. For storage, use a relational on-device database — drift 2.34.3 (Flutter, reactive queries + isolates) or Room 2.8.4 (Android/KMP since 2.7.0) — because the domain (exams / students / answer keys / results / per-question responses) is inherently relational and needs SQL aggregation (count/sum/avg/group-by) for class analytics; avoid Isar (original abandoned, isar_community fork only does bugfixes) and treat Hive CE 2.19.3 / ObjectBox 5.3.2 as complements for blobs, not the primary store. Sharing goes through the Android share sheet (share_plus 13.3.0 `ShareParams.files` + a FileProvider content URI — sharing app-sandbox paths to WhatsApp is a documented failure), with the WhatsApp Business Cloud API (per-message pricing since July 1, 2025, template approval, India INR-billing migration deadline Dec 31, 2026) reserved for automated bulk delivery once a backend exists. When results sync, PocketBase (v0.40.1, single Go binary, SQLite, realtime, official Dart SDK 0.25.0) is the right-sized aggregation backend for a coaching institute, with Supabase + PowerSync as the upgrade path for true offline-first multi-device sync, and Gotenberg (Docker, Chromium/LibreOffice) for server-rendered PDF reports.
 - PDF (Flutter): `pdf` package v3.13.0 (publisher nfet.net, Apache-2.0, ~1.34M weekly downloads) is pure Dart with a Flutter-like widget system (`pw.Widget`). `MultiPage` gives automatic pagination with repeating headers/footers and `NewPage()` breaks; `pw.Table`, `pw.Flex`, `pw.GridView`, `pw.Wrap`, `pw.Column` all split across pages. Units are 1/72 inch; `PdfPageFormat.a4` and inch/cm/mm constants provided. `maxPages` safety limit defaults to 20 — must be raised for a 200-student consolidated class sheet. TTF embedding via `pw.Font.ttf(...)`, Google Fonts via the `printing` package's `PdfGoogleFonts`, emoji via `fontFallback: [emoji]` (Noto Color Emoji). Encryption (RC4-40/128, AES-128/256, SHA1/SHA-256 signatures) moved to the companion `pdf_crypto` package. Deps: archive, barcode, bidi ^2.0.10, crypto, image, vector_math, xml.
 - PDF (Flutter): `printing` v5.15.0 (~795k weekly downloads) provides `Printing.layoutPdf()` (native Android/iOS print service), `Printing.sharePdf(bytes:, filename:)` (direct hand-off to other apps), `Printing.raster(pages:, dpi:)` for PDF→image thumbnails, and a built-in `PdfPreview` widget. iOS needs `use_frameworks!` in the Podfile; macOS needs the `com.apple.security.print` entitlement.
 - PDF (Android native): `android.graphics.pdf.PdfDocument` + Canvas is the zero-dependency route — you manually draw headers, tables and grades onto `PdfDocument.Page` (API reference at developer.android.com/reference/android/graphics/pdf/PdfDocument). It is silent/headless (no dialog), unlike the WebView print path. AndroidX also offers `PrintedPdfDocument`. Commercial alternatives: Nutrient (ex-PSPDFKit), Apryse.
 - PDF via printable HTML: Android's official WebView route (`PrintManager` + `webView.createPrintDocumentAdapter(jobName)`, available since API 19) requires triggering inside `onPageFinished()` and holding a WebView reference (GC'd WebView = failed job). Documented limitations: NO headers/footers/page numbers, no page-range printing, one print job per WebView at a time, CSS print attributes (e.g. landscape) unsupported, JS cannot trigger printing, and it always opens the system print dialog (user picks 'Save as PDF' — cannot be silent).
 - PDF via HTML on-device (Flutter): `htmltopdfwidgets` v2.1.1 converts an HTML subset (h1–h6, p, span, b/i/u, div/section/header/footer, ul/ol/li, table/thead/tr/th/td, a, img network/local/Base64) into `pw.Widget` lists for the `pdf` package — output is widgets, not a finished PDF. CSS subset: box model (width/height/padding/margin/border/border-radius/background-color), basic flexbox, inline color/font-size/text-align; 1px→0.75pt scaling; intelligent pagination/table breaking. No grid, no JS, forms limited to checkboxes; advanced fonts (Arabic/Kanji/emoji) need manual fontFallback.
 - Excel (Flutter): `excel` v4.0.6 (justkawal, MIT, ~306k downloads) reads/writes XLSX with 182 font families, 14 border styles, text rotation −90..90°, merge/unmerge, multi-sheet create/copy/rename, find-replace, RTL — but has NOT been updated in ~2 years and has no CSV support. `excel_plus` v2.16.0 (almasum.dev) is an actively maintained, API-compatible fork claiming ~6.5x faster encoding on a 1M-cell sheet; it adds legacy .xls read, chart read/write (column/bar/line/pie/doughnut/scatter/radar + sparklines), a formula engine with ~160 built-in functions and incremental recalculation, and CSV import/export (via csv_plus) plus JSON export; pure Dart, all platforms. `syncfusion_flutter_xlsio` v34.2.5 is write-only XLSX with formulas, global styles, conditional formatting, PNG/JPEG images (no CSV); commercial but free Community license available; charts require the companion `syncfusion_officechart` package.
 - CSV (Flutter/Dart): `csv` package v8.0.0 implements RFC 4180 (default CRLF line delimiter), configurable single/multi-char delimiters (`,` `::` `|`) and quote/escape chars, auto-detection of `,` `;` `\t` `|`, true StreamTransformer encoders/decoders (one row per event) for memory-safe streaming of large exports, optional dynamicTyping (~15% perf cost), and `decodeWithHeaders()` for map-like rows. It ships an explicit Excel-compatible encoding mode (UTF-8 BOM + `;` separator) — the BOM is what makes Excel open UTF-8 CSVs (Indian-language names) without mojibake. Breaking change in v8: `Csv` no longer extends `dart:convert` Codec — use `asCodec()`.
 - Excel (Android native): Apache POI is a poor fit — `XSSFWorkbook` holds the entire document DOM in memory (documented OOM cases at 4M+ cells, Stack Overflow 19192651; official limitations page poi.apache.org/components/spreadsheet/limitations.html) and the JAR is heavy for DEX/method-count limits. `SXSSFWorkbook` streams rows to temp files for writing but can't read/modify existing files. Lighter alternatives: Fastexcel (streaming writer), Kotlin-native lightweight xlsx libs, or plain CSV. XLSX is just zipped XML, so hand-rolling a minimal writer is also viable.
 - Database (Flutter): drift v2.34.3 (simonbinder.eu, MIT, ~1.14M weekly downloads, all 6 platforms incl. web) is SQLite-backed (`sqlite3 ^3.4.0`) with reactive Streams from any query (joins, WITH, WINDOW), SQL-in-Dart DSL, compile-time-checked queries, built-in migrations, DAOs, transactions, and built-in isolate support so heavy writes (batch-saving 200 graded sheets) never block the UI. Important gotcha from the drift docs: SQLite does not enforce foreign keys by default — issue `PRAGMA foreign_keys = ON` in a post-migration callback. Type converters and `intEnum`/`textEnum` handle custom/enum columns.
 - Database (Android native): Room 2.8.4 (Nov 19, 2025) is current; 2.7.0 (Apr 9, 2025) made Room Kotlin Multiplatform (Android, iOS, JVM desktop, native Mac/Linux) with Kotlin codegen default, KSP2/Kotlin 2.0, and `BundledSQLiteDriver`; 2.8.0 (Sept 10, 2025) added watchOS/tvOS targets, the `room-sqlite-wrapper` artifact, and RAISED minSDK from API 21 to 23. Room forbids entity-to-entity object references; relationships are FK columns + `@Relation(parentColumn, entityColumn)` with `@Junction` for many-to-many, and the docs now RECOMMEND multimap return types (`Map<User, List<Book>>`, `@MapColumn` for aggregates like COUNT) over intermediate POJOs. The Room Gradle Plugin (since 2.6.0) requires a schema export directory — essential for migration tests.
 - Database (raw SQLite, Flutter): sqflite v2.4.3 covers Android/iOS/macOS (Linux/Windows via `sqflite_common_ffi`, web only experimental via `sqflite_common_ffi_web`). DB operations run on a background thread natively, but transactions are exclusive (no concurrent read/write) and DateTime/bool are not native SQLite types. No reactive queries — you wrap Streams yourself.
 - Database (NoSQL status check): original Isar is effectively abandoned (GitHub issue #1689 'Isar is dead, long live Isar'; PRs merged with failing CI); the `isar_community` fork on pub.dev maintains v3.x bugfix-only releases (e.g. 3.1.0+1) with docs at isar-community.dev. Hive CE v2.19.3 (iodesignteam, ~918k weekly downloads) is the maintained Hive: pure Dart key-value, multi-isolate via `IsolatedHive`, WASM web, DevTools inspector; its benchmarks claim 1M writes in ~20s at ~110MB vs Hive v4's ~85s at ~290MB. ObjectBox v5.3.2 stable (6.0.0-preview.2 available) is an ACID NoSQL store with relations and on-device vector search, but its Data Sync is a separately-licensed commercial offering. None of these give you SQL aggregation (GROUP BY rank/percentile per subject) the way drift/Room do.
 - Sharing (Flutter): share_plus v13.3.0 (fluttercommunity.dev) — the static `Share.shareXFiles()` is deprecated; use `SharePlus.instance.share(ShareParams(text:, title:, files: [XFile(...)]))`. `ShareParams` fields include `subject`, `uri`, `fileNameOverrides`, `sharePositionOrigin` (required to anchor iPad popovers), `downloadFallbackEnabled`. Returns a `ShareResult` with status success/dismissed/unavailable. `XFile.fromData()`'s `name` is ignored on most platforms — pass `fileNameOverrides` and clean up the temp cache files it writes. Toolchain floor: Flutter >=3.38.1, Dart >=3.10, Java 17, Kotlin 2.2.0, AGP >=8.12.1, Gradle >=8.13. The `printing` package's `sharePdf()` is a simpler alternative when the payload is already PDF bytes.
 - Sharing (Android mechanics): files must be handed over as content URIs. FileProvider setup (official guide): declare `<provider android:name="androidx.core.content.FileProvider" authorities="<pkg>.fileprovider" grantUriPermissions="true" exported="false">` in the manifest plus `res/xml/filepaths.xml` declaring `<files-path>`/`<external-path>`/`<cache-path>` entries — XML is the ONLY way to declare shared dirs (no programmatic API). `FileProvider.getUriForFile()` returns `content://<authority>/<name>/file.pdf`, sent with `FLAG_GRANT_READ_URI_PERMISSION`. Known failure (fluttercommunity/plus_plugins issue #2828): sharing a PDF to WhatsApp on Android 11 fails when the path is the app sandbox (`/data/user/0/...`) — the fix is a FileProvider content URI and correct MIME type `application/pdf`.
 - Sharing (WhatsApp caveats): share_plus docs explicitly warn that sharing to Meta-owned apps (WhatsApp/Facebook) is unreliable on Android/iOS due to Meta's restrictions, and bugs tied to specific third-party apps' share implementations are closed as wontfix. SUMMARY: Research across OMR vendors (Addmen, Datatec, OMR Master, Verificare/OMR Home, Remark/Gravic, oscan.in), academic surveys (IJERT), and open-source implementations (OMRChecker, PyImageSearch) shows a strong consensus on what makes an OMR sheet readable: bubbles around 3-5 mm (2.98 mm exact on Indian 48-channel scanners, 10-14 pt / ~3.5-4.9 mm per Remark, 3.3 mm default per OMR Master), oval shapes printed with thin uniform outlines in a drop-out color (red/orange/magenta for bubbles, always black for timing tracks and corner fiducials), generous pitch (bubbles never touch, ~1.5x bubble-size center spacing, >=3/8 in / 9.5 mm quiet zones around data areas, 10 mm page margins), and explicit registration geometry: 3-4 solid black corner boxes of 0.25-0.75 in with >=0.125 in white surround for camera/scanner software, plus a black edge timing track (one short mark per row, >=5 mm from the paper edge) for row indexing and legacy-scanner compatibility. For a phone-camera system the deciding factors are pixels-per-bubble (target >=40 px; detection breaks down near 20-30 px), perspective correction from corner fiducials (4-point transform; printed physical markers measurably raise mobile accuracy in OMRChecker from ~90% to near-scan-grade), adaptive per-region thresholding rather than a fixed global threshold, and matte 100-120 gsm uncoated paper printed by a single offset/laser process with sub-mm registration to avoid drift across 50+ rows. Roll numbers are conventionally encoded as one bubble column (0-9 stacked) per digit; sheet identity is carried by a Code 39/128 barcode or QR (4-module quiet zone, error-correction level M) plus a printed serial.
 - Bubble diameter used by real systems: Indian OMR vendor Datatec specifies bubbles of exactly 2.98 mm aligned to the 48-channel OMR scanners predominant in India; OMR Master defaults to 3.3 mm with a typical 3-4 mm range; Remark Office OMR recommends bubble height of 10-14 pt (about 3.5-4.9 mm, never below 10 pt); Verificare/OMR Home lists a minimum of 0.098 in x 0.098 in (~2.5 mm).
 - In digital-image terms, vendors recommend a bubble render at 40-50 px in the scanned image (Addmen), an academic fault-tolerance paper uses ~30 px as typical bubble size, and the PyImageSearch reference pipeline filters bubble contours at width and height >= 20 px with aspect ratio between 0.9 and 1.1.
 - Bubble shape: Remark Office OMR states ovals give the best recognition because any complete shape (circle, square, triangle) works but ovals are easiest to fill completely; it recommends the Gravic OMR font or a capital 'O' in Arial and explicitly advises against Times New Roman. Wikipedia notes US/Europe forms mostly use 'lozenge' (tick-in-rectangle) marks, which are easier to mark and erase, while large bubbles date from insensitive early machines.
 - Outline weight is a failure mode: Addmen lists thick bubble borders as a top design mistake because heavy outlines risk being read as filled marks - outlines should be thin and uniformly printed; Wikipedia similarly reports misreads when oval outlines are too thick or irregular.
 - Text printed inside bubbles must be thin and small; oversized or bold in-bubble labels get detected as dark marks because the reader 'simply responds to the darkened part' (Addmen).
 - Spacing rules: bubbles must never touch or overlap (Addmen, Remark); Remark requires at least two character spaces between adjacent bubbles and a quiet zone of at least 3/8 in (~9.5 mm) between any text, lines, or graphics and bubble areas, OCR zones, or barcodes; OMR Master warns that even 0.5 mm of misalignment compounds across 50 rows.
 - Concrete pitch data point: OMRChecker's sample template uses bubbleDimensions of 40x40 px with bubblesGap of 59 px for MCQ blocks and 46 px for digit (0-9) blocks - i.e., center-to-center pitch of roughly 1.5x the bubble size, leaving about half a bubble diameter of clear space between outlines.
 - Registration marks for image-based reading (Remark Office OMR v12+ 'anchor marks'): use 3 or 4 dark corner boxes sized 0.25 in (6.35 mm) minimum to 0.75 in (19 mm) maximum, each with at least 0.125 in (3.2 mm) of white space around it; the software searches a 1.25 in x 1.25 in corner window; orientation disambiguation requires either one notably larger/smaller anchor, two anchors sharing a side, or exactly 3 anchors; graphics must not sit beside anchors or auto-anchoring misidentifies them.
 - Indian vendors confirm the same convention: four corner 'index points' (Addmen) are mandatory for scanner alignment and must be cleanly printed and undistorted with whitespace around them; Mindee describes registration marks as solid black squares or circles in page corners; OMR Master says 4-corner black squares establish the coordinate system and compensate for minor shifts.
 - Timing tracks: hardware OMR uses 'short black lines printed at the edge of the form, one mark per line' that trigger a read pulse per row as the transport feeds the paper (OMR Solutions); Datatec requires a precise minimum 5 mm gap between timing track and paper edge to prevent scanner rejection; oscan/omrsheet.com states timing tracks are always printed black. LEADTOOLS notes software OMR engines can process forms with or without timing marks.
 - Roll-number/ID encoding is a grid field: one column of 10 digit bubbles (0-9) per digit position - e.g., a phone number or ID as 10 columns of 10, a date as six columns of 10, a name as 26 columns (Wikipedia grid fields); OMR Master describes 'bubble-row fields for encoding student IDs digit by digit'; OMRChecker models this as fieldType QTYPE_INT (vertical digits 0-9) with customLabels merging roll1..roll9 into one Roll column.
 - Sheet ID symbologies: Datatec specifies Code 39 or Code 128 barcodes plus a unique printed serial per sheet; QR Code requires a 4-module quiet zone on all four sides (Denso Wave); a Version-3 QR (29 modules) at 0.254 mm/module measures 7.37 mm plus margins = 9.4 mm total, with error-correction Level M cited as the standard choice.
 - Drop-out color practice: pre-printed bubble outlines and form furniture are printed in a color the reader ignores - visible red for pencil-reading heads, orange/light blue or magenta/red variants on Indian sheets (oscan: 'timing tracks always in black, bubbles may be magenta, orange and red'); Datatec adds that blue, brown, and green inks are unsuitable because of higher carbon content and requires low-carbon reflective inks. For scanners with infrared heads, #2 pencil stays dark at IR wavelengths while some inks do not (Pilot Ltd).
 - Phone cameras capture full RGB, so red drop-out ink does not physically disappear - camera-based OMR apps simulate the drop-out digitally via channel subtraction or color thresholding (Mindee + camera-OMR apps); this makes drop-out color a software decision in a mobile system rather than a hardware one.
 - Paper stock: Indian OMR sheets use 105-120 GSM maplitho (oscan, Datatec, Wikipedia); Remark recommends 20 lb (~75 gsm) for single-sided forms and 24-28 lb for double-sided; carbonless multi-part sets use a 105 gsm top sheet plus 60-70 gsm subsequent sheets. Paper must be opaque and moisture-resistant; humidity and heat expand paper and shift bubbles off sensor positions (Pilot Ltd).
 - Print precision and process: OMR layouts must be designed to 0.05 mm precision (Wikipedia); Addmen stresses that DTP-drawn sheets are invalid until calibrated in OMR software and that no element may be shifted after layout finalization; Remark says laser printers/MFPs are fine but all forms should come from the same device or same photocopy batch (consistent alignment and toner), that photocopying limits tolerance for offset/skew so margins must be generous, and that the template should be built from the copy, not the original.
 - Standard sheet formats: Indian OMR A4 is 8.25 x 11.25 in and OMR legal is 8.25 x 14 in (oscan, Datatec), slightly narrower than true A4 (8.268 x 11.693 in) to fit 48-channel transports; A5 (5.827 x 8.268 in) and US Legal (8.5 x 14 in) also appear (OMR Home).
 - Margins and quiet zones for capture robustness: OMR Master recommends 10 mm margins on all sides to keep content safe from print/scan cutoff; Remark requires 3/8 in quiet zones around data areas, no lines or boxes around/between bubbles, and no shading in OMR data areas (if shading is unavoidable use 5-10% gray that drops out - and never photocopy shaded forms, which introduces speckles).

 - ANDROID OFFLINE-FIRST, AUTHORITATIVE PATTERN (Google's own docs): every network-backed repository needs exactly two data sources — a Local source (Room for relational, DataStore for key-value/protobuf) that is the canonical SOURCE OF TRUTH and the sole source of reads, and a Network source that only updates the local one. Domain/UI layers must never touch the network directly. Reads are exposed as Kotlin Flow; error handling uses LCE sealed classes (Loading/Content/Error) with the catch operator. (developer.android.com/topic/architecture/data-layer/offline-first)
 - ANDROID WRITE STRATEGIES (same source): (1) online-only writes for true transactions, (2) QUEUED writes — insert into a queue and drain with exponential backoff via WorkManager, (3) LAZY writes — write local first, notify network later (best for critical data; this is the right one for graded sheets). Google also notes an offline-first app does NOT need offline writes to qualify — offline READS are mandatory, offline writes are optional.
 - ANDROID WORKMANAGER RECIPE (from the Now in Android sample, github.com/android/nowinandroid): enqueueUniqueWork(name, ExistingWorkPolicy.KEEP, ...) at app startup; Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED); setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST); CoroutineWorker returns Result.retry() and WorkManager applies exponential backoff automatically. For strict ordering, back the queue with Room and drain sequentially.
 - CONFLICT RESOLUTION, GOOGLE'S STATED DEFAULT: 'the most common mobile approach is last write wins — devices attach timestamps; the network discards older data,' generally layered with versioning/metadata. For your domain you can do better than LWW because graded sheets are append-only immutable facts keyed by a client-generated UUID — the only genuinely mutable/conflictable entities are answer keys and sheet templates, which you should make immutable-by-version rather than updatable-in-place.

Concretely: client generates a UUID per scan, server enforces a unique constraint on (institute_id, exam_id, scan_uuid) and upserts ON CONFLICT DO NOTHING, so a re-sent sheet can never double-count in the merit list.

 - MULTI-TENANT POSTGRES — THREE PATTERNS, CLEAR CONSENSUS: (a) shared schema + tenant_id column + RLS — best for most SaaS and high tenant counts, isolation is logical not physical; (b) schema-per-tenant — practical ceiling around ~1,000 tenants due to catalog bloat and migration complexity; (c) database-per-tenant — strongest isolation and per-tenant backup/restore, highest operational cost, hardest cross-tenant aggregation, reserved for enterprise/compliance-heavy customers.  - RLS PRODUCTION PATTERN (exact mechanics): inside a transaction run SELECT set_config('app.tenant_id', $1, true) — the third argument true is critical, scoping the GUC to the transaction so it cannot leak to the next pooled request; policy is USING (tenant_id = current_setting('app.tenant_id', true)::uuid) with WITH CHECK on writes to block cross-tenant inserts; also run ALTER TABLE ... FORCE ROW LEVEL SECURITY because table owners bypass policies by default. The second true in current_setting makes an unset GUC return an empty string that casts to a null uuid and denies all rows — 'the failure mode is zero rows, not a leaked row.' (theroadtoenterprise.com/blog/postgres-rls-multi-tenant-saas)
 - RLS PERFORMANCE + PITFALLS: every policy-referenced column needs an index or plans degrade to a seq scan with a filter ('potentially an order of magnitude slower'); use composite indexes led by tenant_id, e.g. (tenant_id, created_at DESC), to keep the policy filter and the sort in one scan. PgBouncer must run in transaction mode (not session) so connection lifetime matches the GUC's transaction lifetime. Documented pitfalls: SET outside a transaction contaminates reused pooled connections; ORMs bypass the GUC unless routed through a single withTenantTx wrapper with the raw client unexported; SECURITY DEFINER functions are documented policy bypasses. Also note RLS gives row isolation only — it does not limit disk, CPU, or cache per tenant. (theroadtoenterprise.com; thenile.dev/blog/multi-tenant-rls)

RECS:
 * ADOPT HYBRID WITH ON-DEVICE AS THE SYSTEM OF RECORD FOR CAPTURE-TO-GRADE. Concretely: (1) on-device capture with ML Kit Document Scanner (edge detection + perspective correction + shadow/finger cleanup, no camera permission needed); (2) on-device registration via your own printed timing marks and a perspective warp to canonical template coordinates; (3) on-device bubble detection with OMRChecker-style local thresholding (port the MIN_JUMP / GLOBAL_PAGE_THRESHOLD logic from OpenCV/Python to OpenCV4Android or pure Kotlin); (4) on-device grading against the answer key; (5) upload the warped/normalized image + per-bubble confidence values + results to the server. The server is an auditor and aggregator, never a prerequisite for grading.
 * DESIGN FOR HUMAN REVIEW FROM DAY ONE — this is how you close the ~90%-on-mobile accuracy gap. Tag every detection with a confidence score (bubble-mean jumps, OMRChecker's MIN_JUMP_STD / GLOBAL_THRESHOLD_MARGIN logic), and auto-route low-confidence sheets and multi-marked/unmarked roll numbers to a review queue. OMRChecker's own filter_out_multimarked_files option (which quarantines multi-marked sheets instead of evaluating them) is the precedent. Budget UI for this now: an operator tapping the correct bubble on a zoomed crop is 5-10 seconds per flagged sheet and takes effective accuracy from ~90% to ~99%+.
 * SHIP DETECTION TUNING AS REMOTE CONFIG, NOT CODE. Keep the detection engine stable in the APK and push three things from the server: sheet template JSON (layout, per OMRChecker's template.json schema: fieldBlocks, origins, gaps, QTYPE_MCQ4/QTYPE_INT, customLabels for roll digits), threshold config JSON (the MIN_JUMP family), and answer keys. Version every template and every answer key immutably (template v3, key v2) and have results reference the version used — this turns 'the answer key was wrong, regrade 4,000 sheets' into a cheap server-side recompute instead of a re-scan, and eliminates your only real write-conflict class.
 * BUILD THE ANDROID DATA LAYER ROOM-FIRST PER GOOGLE'S OFFICIAL OFFLINE-FIRST PATTERN: Room is the source of truth and the only thing the UI reads (via Flow); a repository owns a network data source whose only job is to update Room; WorkManager drives a single sync worker with NetworkType.CONNECTED, enqueueUniqueWork + ExistingWorkPolicy.KEEP, Result.retry() for automatic exponential backoff. Use LAZY WRITES (write local first, notify network later) — graded sheets are critical data. Do NOT couple the app to Supabase's lack of offline support; the local layer is yours either way.
 * MAKE SYNC IDEMPOTENT BY CONSTRUCTION, NOT BY CARE. Client generates a UUID4 per scan at capture time; the server has a unique constraint on (institute_id, exam_id, scan_uuid) and upserts ON CONFLICT DO NOTHING. Results are append-only immutable facts, so genuine conflicts are near-impossible. Do not use last-write-wins on anything that matters; reserve LWW (Google's stated mobile default) for genuinely ephemeral state like UI prefs. Because offline sync replays operations, every server write path must tolerate receiving the same sheet twice.
 * GO MULTI-TENANT (shared schema + tenant_id + RLS) FROM THE FIRST COMMIT even though you are launching with one institute. A nullable-free institute_id/tenant_id UUID column on every row plus RLS policies costs hours now and a rewrite later. Supabase enables RLS by default on new tables as of 2026, and RLS covers every access path (API, direct SQL, cron, migrations) unlike Firebase rules which the Admin SDK bypasses. Use set_config('app.tenant_id', $1, true) transaction-scoped in Postgres RPCs, or auth.uid()-based policies on institute membership if going through PostgREST directly. Index every tenant table with tenant_id as the leading column.
 * RUN A SINGLE-TENANT DEPLOYMENT AS A PRICED TIER, NOT A SEPARATE CODEBASE. Because your schema is already tenant-scoped, a 'dedicated instance' for a large coaching chain is the same app pointed at a separate Postgres database (database-per-tenant) — which is exactly the pattern enterprises with compliance demands want, gives per-tenant backup/restore and data localization for DPDP, and needs zero code fork. This is the cheapest possible path from one institute to multi-institute SaaS.
 * CHOOSE SUPABASE FOR THE MVP BACKEND. Reasons specific to this domain: (a) the data is deeply relational and your reports are ranking/aggregation-heavy — RANK() OVER (PARTITION BY ...), subject-wise cutoffs, percentile vs cohort, cohort analytics across exams are single SQL statements in Postgres and read-amplification nightmares in Firestore; (b) RLS in SQL gives you multi-tenant SaaS for free as you grow; (c) Storage has built-in image transformations + CDN, ideal for review-queue thumbnails; (d) $25/mo Pro covers an entire institute's first year; (e) it is standard Postgres, so exit is measured in weeks. Pair it with Kotlin Multiplatform's community supabase-kt (the JS client is the only official one — accept this tradeoff).
 * CHOOSE FIREBASE INSTEAD ONLY IF one of these is true: your team is already deep in it, you need genuine realtime collaboration as a core feature (multiple operators watching one live queue), or you want offline sync without writing any Room/WorkManager code. Even then, note Firestore's free tier is 50K reads/DAY (vs Supabase's unlimited API requests) and a marks-sheet dashboard is precisely the no-joins read-amplification case that makes Firestore expensive. Do not build a custom backend for MVP — you gain nothing you need and lose auth, storage, and RLS.
 * STAY DELIBERATELY OFF POWERSYNC/ELECTRICSQL FOR MVP. Your sync is one-directional burst-upload (scans up) plus occasional pull (reports, answer keys, templates down) — Room + WorkManager + Supabase REST handles this in a few hundred lines. Add PowerSync only when you need live bidirectional sync of operational state across devices (its Postgres-to-client-SQLite replication with a Kotlin/Android SDK is the right tool then). Adding a sync engine before you need it is the most common way to over-engineer an MVP.
 * ARCHITECT FOR DPDP AS DATA PROCESSOR, NOT FIDUCIARY. Contract with each institute so the INSTITUTE is the Data Fiduciary and your app is the Data Processor — this converts the (deferred-to-May-2027) verifiable-parental-consent burden into a strong Data Processing Agreement plus minimization discipline. Concretely: collect roll number and marks, not names/addresses/phone numbers; treat the roll-number-to-identity mapping as the institute's data, held in their tenant, never pooled across tenants; store the smallest image that supports audit (the warped grayscale crop plus the annotated overlay, not the 12MP original); publish and enforce a retention schedule with automatic erasure; keep student PII out of any analytics or ML training set; prefer India-region hosting for data-localization exposure.
 * SOLVE IMAGE STORAGE COSTS WITH A TRANSFORM AT UPLOAD. A 12MP sheet JPEG is 3-5 MB; a 200-student exam is ~1 GB and a 100-exam year is ~80-100 GB — which blows through Supabase Pro's 100 GB in year one. At upload time, derive and keep (a) the warped grayscale normalized crop for re-detection, and (b) a JPEG thumbnail plus the annotated detection overlay for the review console; drop the full-res original after a short grace window or push originals to cheaper object storage (S3/R2) keeping only metadata in Supabase. Supabase's built-in image transformations handle the thumbnail resizing.
 * TREAT APP-SIDE DETECTION AS A REPRODUCIBLE PIPELINE FOR DEBUGGING: save per-bubble confidence metrics alongside every result (OMRChecker's save_image_metrics does exactly this) and render annotated debug overlays (its draw_question_verdicts / draw_detected_bubble_texts options — lightgreen correct, red incorrect, + o - * verdict symbols). When an institute reports a wrong result, you want the exact warped crop and per-bubble numbers, not a he-said-she-said argument. This also becomes your labeled dataset if you ever train a learned model.
 * PLAN THE iOS PORT AROUND SHARED SPEC, NOT SHARED CODE. Your real cross-platform assets are the sheet template JSON schema, the threshold config, the answer-key format, and the Postgres schema — keep all four canonical and versioned on the server from day one. Then the Android detection engine (OpenCV4Android) and a later iOS engine (Vision + custom Core Image / Metal, or OpenCV iOS) are independent implementations of the same published spec. Validate portability with a golden-image test set (sheet photos + expected detection JSON) that runs against every engine. Avoid premature Kotlin Multiplatform for the CV core.

 - Classical pipeline reference implementation (PyImageSearch bubble-sheet grader, still the canonical OpenCV recipe): grayscale -> cv2.GaussianBlur((5,5),0) -> cv2.Canny(blurred, 75, 200) -> cv2.findContours(RETR_EXTERNAL, CHAIN_APPROX_SIMPLE) sorted by cv2.contourArea descending -> cv2.approxPolyDP(c, 0.02*cv2.arcLength(c,True), True) until a 4-point polygon is found -> cv2.getPerspectiveTransform + cv2.warpPerspective for top-down view. Bubble stage: cv2.threshold(warped, 0, 255, THRESH_BINARY_INV | THRESH_OTSU), contour filter w>=20 and h>=20 and 0.9 <= w/h <= 1.1, then per-bubble mask via cv2.drawContours(-1 filled) + cv2.bitwise_and and cv2.countNonZero; the marked answer is the bubble with the largest non-zero count in each row.
 - The PyImageSearch grader's two documented blind spots are exactly the ambiguous-mark cases: with no minimum floor on the countNonZero total, a fully blank row still returns whichever bubble has the relative maximum (skipped question misread as an answer), and multiple marks in one row are not detected. Both fixes (floor threshold; invalidate row if two bubbles exceed it) are described but not implemented in the tutorial - a production system must add them.
 - PyImageSearch deliberately rejects Hough circle detection for bubbles: circle detection parameters are hard to tune per image and Hough circles 'don't handle deformations in their outlines very well' since students often mark slightly outside the lines; contours tolerate imperfectly filled bubbles.

 - OMRChecker pipeline (src/core.py): resize to processing dims (defaults 666x820) -> run template-declared pre-processors -> resize to template pageDimensions + normalize grayscale -> optional auto-align -> per-bubble ROI mean via cv2.mean() -> two-tier thresholding -> CSV + annotated overlay image.
 - OMRChecker auto-align detail (instructive): CLAHE is applied ONLY to a morphological copy, never to the thresholding copy (code comment: 'clahe is good for morphology, bad for thresholding'). Uses GAMMA_LOW=0.7, THRESH_TRUNC at 220, vertical-line extraction via MORPH_RECT (2,10) kernel iterations=3, TRUNC at 200, invert, binary threshold with morph_thr=60 for mobile images vs 40 for scanned, then erode np.ones((5,5)) iterations=2. Per-block search shifts left/right comparing vertical margin strip means against 100, up to max_steps=20 at stride=1. Defaults ship with auto_align=False.
 - OMRChecker thresholding is adaptive 'largest-gap', not a fixed cutoff. Global tier: sort all bubble means, find the biggest jump (looseness=4), thr = q_vals[i-ls] + jump/2, seeded at MIN_JUMP=25. Local per-question-strip tier: largest adjacent gap on that strip's sorted means; falls back to global if fewer than 3 values or spread <= MIN_GAP=30. Confidence proxy is jump magnitude vs MIN_JUMP + CONFIDENT_SURPLUS (=30); the low-confidence branch is literally 'pass' with a TODO. Baselines: GLOBAL_PAGE_THRESHOLD_WHITE=200, GLOBAL_PAGE_THRESHOLD_BLACK=100 (PAGE_TYPE_FOR_THRESHOLD default 'white'). Other tuning constants: JUMP_DELTA=30, MIN_GAP=30.
 - OMRChecker mark decision: bubble_is_marked = (per_q_strip_threshold > bubble_mean), i.e. darker than threshold = marked. Outlier gating: no_outliers = strip_std < global_std_thresh (handles all-black / all-white strips). Multi-mark is flagged when a field_label is already present in omr_response; empty strip yields field_block.emptyValue. There is NO explicit numeric confidence score emitted per bubble or per sheet - confidence is implicit in gap magnitude and std tests.
 - OMRChecker registration via CropOnMarkers: marker image loaded grayscale, Gaussian blurred, NORM_MINMAX, optionally erode-subtracted. Scale sweep np.arange(100, 35, -6) i.e. 35-100% in 10 steps (defaults marker_rescale_range=(35,100), steps=10), each step cv2.matchTemplate with TM_CCOEFF_NORMED, tracking best res.max(). Image split into 4 quadrants at midlines (QUADRANT_DIVISION height_factor=3, width_factor=2) with 2px white separators so a match cannot straddle a midline; marker matched independently per quadrant. A quadrant fails if max_t < 0.3 (min_matching_threshold) OR abs(all_max_t - max_t) >= 0.41 (max_matching_variation). sheetToMarkerWidthRatio default 17 (marker is ~1/17 of sheet width). Then four_point_transform on the ORIGINAL image using the four marker centers.
 - OMRChecker alternate registration: CropPage (morphology-based page finding, morphKernel default [10,10]) and FeatureBasedAlignment (maxFeatures, goodMatchPercent, reference image - feature matching). Constants for page finding: MIN_PAGE_AREA_THRESHOLD=80000, MAX_COSINE_THRESHOLD=0.35, PAGE_THRESHOLD_PARAMS threshold_value=200/max_pixel_value=255, CANNY_PARAMS lower=185/upper=55, APPROX_POLY_EPSILON_FACTOR=0.025, EROSION_PARAMS kernel (5,5) iterations 5, DEFAULT_BORDER_REMOVE=5.
 - OMRChecker template format: JSON Schema draft 2020-12, additionalProperties:false everywhere, required = [bubbleDimensions, pageDimensions, preProcessors, fieldBlocks]. Coordinates are PIXELS on the page AFTER it is resized to pageDimensions (canonical normalized space) with origin top-left, y down. Top-level keys: bubbleDimensions [w,h], pageDimensions [w,h], customLabels (fields joined into one output column, e.g. roll digits 'roll1..9' -> Roll), outputColumns (ordered CSV columns), preProcessors, fieldBlocks, emptyValue.
 - OMRChecker fieldBlocks geometry: each block requires origin [x,y], bubblesGap, labelsGap, fieldLabels, plus either fieldType OR (bubbleValues + direction). direction is 'horizontal' or 'vertical' and selects which axis advances for bubble values vs field labels. Generation is purely additive: lead_point starts at origin; inner loop appends a Bubble then advances bubble_point[_h] += bubbles_gap; outer loop advances lead_point[_v] += labels_gap. Block extent = gap*(count-1) + bubble_dimension. Validation rejects blocks where origin+dimensions exceed page_dimensions. This 'origin + two gaps + direction' model is extremely compact and proven - strongly recommend adopting it.
 - OMRChecker FIELD_TYPES presets (src/constants/common.py): QTYPE_INT = digits 0-9 vertical; QTYPE_INT_FROM_1 = 1-9 then 0 vertical; QTYPE_MCQ4 = A,B,C,D horizontal; QTYPE_MCQ5 = A-E horizontal; QTYPE_MCQ4_RTL and QTYPE_MCQ5_RTL = right-to-left variants. Field labels support range expansion (e.g. 'q1..20'). Per-block overrides of bubbleDimensions and emptyValue are supported.
 - OMRChecker preProcessor options are schema-validated per name: CropOnMarkers (apply_erode_subtract, marker_rescale_range, marker_rescale_steps, max_matching_variation, min_matching_threshold, sheetToMarkerWidthRatio, relativePath required); CropPage (morphKernel); FeatureBasedAlignment (2d, goodMatchPercent, maxFeatures, reference required); GaussianBlur (kSize, sigmaX); Levels (gamma, high, low each 0-1); MedianBlur (kSize). v2 renames pageDimensions->templateDimensions and adds top-level/blocks-level processingImageShape, outputImageShape, and conditionalSets.
 - OMRChecker evaluation format (src/schemas/evaluation_schema.py): requires source_type ('csv'|'custom'), options, marking_schemes. Question types: standard string, multiple-correct array (['A','B']), multiple-correct-weighted ([['A',1],['B',2]] or ['AB',2]). marking_score accepts a number or a string matching '-?(\d+)(/(\d+))?' enabling negative marking (-1) and fractional/partial marking (1/4). Every marking object must define correct, incorrect AND unmarked. Per-subject/section schemes via named keys carrying 'marking' + 'questions'. Streak-based marking is an explicit TODO.

So the canonical page size is arbitrary per template - it is a self-relative coordinate space.

RECS:
 * Adopt OMRChecker's two-tier adaptive 'largest-gap' thresholding rather than any fixed pixel threshold: compute a global threshold across all bubble means on a page, then a per-question-strip local threshold from the largest adjacent gap, and mark a bubble when its mean is darker than the strip threshold. Use OMRChecker's starting constants as your baseline (MIN_JUMP=25, CONFIDENT_SURPLUS=5, MIN_GAP=30, JUMP_DELTA=30, white-page baseline 200 / black-page 100) and re-tune for camera capture. This is the single most valuable algorithmic idea to port - it is what makes detection robust to uneven phone lighting that defeats fixed thresholds.
 * Make the printable PDF and the detection template ONE machine-readable source of truth (the SDAPS/Aspose model). Author the sheet once in a declarative spec, and derive both (a) the print PDF and (b) the detection grid from it. This eliminates the entire class of template-vs-print drift bugs that OMRChecker's manual JSON authoring + iterative --setLayout workflow suffers from. Prefer a human-readable Aspose-style text markup ('?answer_sheet questions=180 options=4 columns=4') layered on top of, or compiled down to, a JSON grid model for the runtime.
 * Use OMRChecker's fieldBlock model for the grid: origin [x,y] + bubblesGap + labelsGap + direction ('horizontal'/'vertical') + fieldType preset + fieldLabels. It is compact, purely additive geometry, trivially validated, and proven across the many community templates. Add: explicit named FIELD_TYPE presets for your needs (MCQ4/MCQ5, INT 0-9 vertical digit grid for the roll number, RTL variants), per-block bubbleDimensions and emptyValue overrides, and range-expanded field labels ('q1..180').
 * Define template coordinates in a canonical normalized space (OMRChecker resizes every image to template pageDimensions before reading; community templates range from 299x398 to 1846x1500, proving the space is arbitrary and self-relative). Better: author in real print units (mm at target DPI) and compile to a canonical detection space, so PDF generation and detection can never disagree. Validate with JSON Schema draft 2020-12 and additionalProperties:false exactly as OMRChecker does - it catches template typos at load time.
 * For registration, use four registration markers found by quadrant-restricted template matching (OMRChecker's CropOnMarkers) as your primary anchor: scale sweep 35-100% in 10 steps with TM_CCOEFF_NORMED, split the image into quadrants with separator lines so a match cannot straddle a midline, reject a quadrant below match score 0.3 or when its score deviates from the global best by >=0.41, then four_point_transform on the ORIGINAL (unprocessed) image using the four centers. Size markers at roughly 1/17 of sheet width. This is far more robust on skewed phone photos than whole-page contour finding.
 * Add L-shaped corner markers as a second, redundant anchor type from day one. OMRChecker issue #270 (maintainer-filed, 'good first issue') notes many real OMR sheets use L-shaped corners and that supporting them would 'increase accuracy and success rate'. Since you control the sheet design, print both markers and L-corners and let detection prefer whichever resolves with higher confidence - a cheap form of redundancy for glare/occlusion.
 * Put an identification code ON the sheet and read it: a QR code (as SDAPS does for multipage identification) encoding sheet-type ID + template version + optionally an exam ID, plus the bubbled roll-number digit grid (OMRChecker's QTYPE_INT vertical 0-9 grid with customLabels joining digits into one output column). The QR removes all ambiguity about which template to apply and enables multi-page and multi-variant sheets (correctAE's 6-variant equivalence-table feature is the coaching-institute pattern to copy).
 * Emit an explicit numeric confidence per bubble, per question and per sheet. OMRChecker has no such score (confidence is implicit in gap magnitude and strip-std tests, and the low-confidence code path is literally a TODO 'pass'). Compute confidence from the gap magnitude relative to MIN_JUMP + CONFIDENT_SURPLUS, the strip std vs global std, and the margin between the top and second-brightest bubble. This is what lets a mobile app decide 'accept' vs 'ask the invigilator to re-shoot' vs 'flag for manual review' - the workflow Addmen and Verificare both ship as a 'manual correction interface'.
 * Port the detection core to Kotlin/C++ with OpenCV for Android (current 4.x; note AndroidOMRHelper bundled OpenCV 3.1.0 and its author says it 'needs a huge upgrade'). LazyOMR proves on-device OpenCV is viable even in OpenCV.js at ~3.4MB; native OpenCV will handle 200 questions comfortably. You only need to port core.py's thresholding plus the processors - deliberately skip OMRChecker's pandas, matplotlib, rich, screeninfo, deepmerge and PyMuPDF dependencies, which are reporting/CLI-only and useless on Android.
 * Build capture-time validation as a first-class gate (the AndroidOMRHelper concept, which is exactly why OMRChecker's author wrote it): live camera edge overlay to frame the sheet, plus pre-flight checks for blur, glare/overexposure, low contrast, and all four markers visible. Given OMRChecker's own numbers - near 100% on good scans vs ~90% on mobile images - rejecting bad captures at the camera is worth more accuracy than any detection algorithm improvement. Target a capture resolution comfortably above OMRChecker's 640x480 floor; for a 180-question A4 sheet aim for enough pixels that a bubble spans roughly 20px or more (OMRChecker sample1 uses 40x40px bubbles in canonical space).
 * Steal the specific pre-processing insight from OMRChecker core.py: apply CLAHE only to a morphological/analysis copy and never to the copy you threshold (their comment: 'clahe is good for morphology, bad for thresholding'), and maintain separate morphological thresholds for camera (60) vs scanned (40) input. Also handle the xeroxed-sheet case, where the global threshold collapses to 255 and everything reads as dark.
 * Design the grading/evaluation format up front along OMRChecker's evaluation.json lines but more simply: per-question answer (single, multi-correct array, or weighted), and a marking scheme that must explicitly define correct/incorrect/unmarked scores, supporting negative marking (-1) and fractional partial marking (1/4) - the JEE/NEET requirement. Add per-subject/section marking schemes and post-hoc question cancellation with automatic recalculation (correctAE), plus statistical 'wrong answer key detection' (Verificare) that flags questions where a large majority chose the same non-key answer.
 * Benchmark against the right numbers: OMRChecker's 200 sheets/min on desktop is your reference for native on-device speed (expect slower but adequate - one sheet per photo, not batch); its ~90% mobile accuracy is the number to beat; RescueOMR's ~2% needing manual review across 10,000 documents is a realistic target for a well-designed sheet plus capture validation. LazyOMR's self-assessment ('not suitable for high-stakes exams') marks the quality bar you must clear for Indian coaching-institute use.

===== RESEARCH (agent ac1809af) =====
SUMMARY: The single-correct/4-option/one-filled-bubble model is insufficient for the Indian coaching market. Verified against primary sources — the official JEE Advanced 2026 Paper 1 & 2 question papers (jeeadv.ac.in PDFs), the NEET (UG) 2026 Information Bulletin, and the JEE Main 2026 Information Bulletin (both NTA bulletins on the Government of India CDN s3waas.gov.in) — the system must support at least four question types: single-correct MCQ (+4/−1 in NEET & JEE Main; +3/−1 in JEE Advanced), multiple-correct with partial credit (+4 full, +3/+2/+1 partial, negative in "all other cases" — the penalty is −1 in 2026 but was −2 in earlier years), integer/numerical digit-grid questions (0–9 bubbles per digit column, 00–99 for two columns), and matrix/list-match questions. Official NTA text defines three distinct outcome states per question (correct / incorrect / unanswered) and explicitly folds multi-marked single-correct responses into "all other cases" = negative marks. Critically, scoring varies by section within the same paper and by year, so marking rules must be versioned configuration data, not code. Commercial Indian OMR software (Addmen, Verificare/OMR Home) and Remark Office OMR all confirm the required architecture: per-set (A/B/C/D) answer keys, flexible per-question marking schemes including negative/partial/bonus/cancellation, wrong-answer-key detection, and — most importantly — key editing and re-grading after reading without rescanning sheets, which is only possible if raw per-bubble reads and sheet images are retained separately from computed scores.
 - OFFICIAL JEE Advanced 2026 Paper 1, Section 2 (verbatim from jeeadv.ac.in PDF): 'Full Marks : +4 ONLY if (all) the correct option(s) is(are) chosen; Partial Marks : +3 If all the four options are correct but ONLY three options are chosen; Partial Marks : +2 If three or more options are correct but ONLY two options are chosen, both of which are correct; Partial Marks : +1 If two or more options are correct but ONLY one option is chosen and it is a correct option; Zero Marks : 0 If none of the options is chosen (i.e. the question is unanswered); Negative Marks : −1 In all other cases.'
 - OFFICIAL JEE Advanced 2026 worked example for a multi-correct question whose correct options are (A),(B),(D): {A,B,D}→+4; {A,B}→+2; {A,D}→+2; {B,D}→+2; {A}→+1; {B}→+1; {D}→+1; no option→0; 'choosing any other combination of options will get −1 marks.' The partial mark therefore equals the count of correct options chosen when the chosen set is a strict subset of the correct set; full +4 requires exact equality; any wrong option present triggers the negative mark. If the key has exactly 1 correct option, choosing it gives +4 (not +1) — partial credit only exists when the key has 2+ correct options.
 - OFFICIAL JEE Advanced 2026 marking varies by section WITHIN one paper. Paper 1: S1 4Q single-correct +3/0/−1; S2 4Q one-or-more-correct +4 with partial/0/−1; S3 4Q numerical-value +4/0 with NO negative; S4 4 Matching-List sets (single-correct form) +4/0/−1. RECS:
 * DROP THE GLOBAL 'double mark = invalid' RULE. Replace it with a per-question mark-count-validity property: SINGLE_CORRECT → max 1 selection; MULTI_CORRECT → 1..N selections valid, N>0 required for credit; INTEGER_DIGITS → exactly 1 selection per digit column; MATRIX → exactly 1 selection per row. Verificare models this as an explicit 'Multiple allowed' layout property, and the JEE Advanced multi-correct scheme is unimplementable without it.
 * MODEL SCORING AS DATA. Create a `scoring_rule` table keyed by strategy + params JSON, referenced per question (with section-level defaults), never a switch statement in code. Concretely ship four strategies: (a) SINGLE_CORRECT {correct, wrong, unattempted, multi_mark_action}; (b) MULTI_CORRECT {full, partial_by_count{1,2,3}, any_wrong, unattempted}; (c) INTEGER {correct, wrong, unattempted, ambiguous_column}; (d) OVERRIDE for dropped/incorrect keys {award_all} . Two shipped presets must be: NEET/JEE-Main {4,-1,0} and JEE-Advanced-2026 multi-correct {4, [1,2,3], -1, 0} plus the legacy {-2} variant, because the negative mark demonstrably changed year to year.
 * IMPLEMENT PARTIAL CREDIT FOR MULTI_CORRECT AS A PURE SET FUNCTION. Let C = chosen set, K = key set. If C = ∅ → unattempted (0). Else if C ⊆ K and C = K → full. Else if C ⊆ K (strict subset) → partial_by_count[|C|]. Else (any element of C not in K) → any_wrong. Note partial only exists when |K| ≥ 2, and this must be validated against the official worked example {A,B,D}: {A,B,D}→+4, {A,B}/{A,D}/{B,D}→+2, {A}→+1, ∅→0, anything containing C→−1.
 * STORE RAW PER-BUBBLE READS, NOT DECODED ANSWERS. Persist for every bubble: fill_ratio (the normalized intensity), mark_class ∈ {FILLED, EMPTY, PROBABLE, MULTIPLE, OVERFILLED, BLANK}, confidence, and the threshold parameter-set id used. Addmen's own taxonomy is 'Probably marked, Multiple marked, Overfilled Bubbles, Blank bubbles' — copy it verbatim so downstream semantics match industry practice. This is what makes 'Edit answer keys after reading … without rescanning sheets' possible, and it also lets you re-run classification with different thresholds from the stored image without re-detecting geometry.
 * USE A THREE-ZONE THRESHOLD, NOT A BINARY CUTOFF. Verificare's 'confidence factor' pre-defines darkness levels with 'maximum and minimum percentages'; Addmen defines a borderline mark as 'an impression which does not fall under the threshold settings range but still large enough to be considered.' Implement fill_ratio < empty_max → EMPTY; > filled_min → FILLED; between → PROBABLE (route to a human-confirmation screen). Treat PROBABLE as unscored-until-confirmed rather than guessing, because a wrong guess is invisible in the final marksheet.
 * MAKE THE ANSWER KEY AN IMMUTABLE, VERSIONED TABLE. Schema: `answer_key_version (id, exam_id, status ∈ {provisional, final}, created_at, created_by, supersedes_id)` and `answer_key_entry (key_version_id, set_code, question_id, correct_options[], correct_integer, state ∈ {normal, multiple_correct_key, all_options_correct, none_correct, dropped})`. Every score row stores the key_version_id that produced it. Re-grading inserts a new version and recomputes — never UPDATE in place.
 * IMPLEMENT THE NTA KEY-CORRECTION POLICY AS A FIRST-CLASS SCORING STATE, because it is the single most common re-grade trigger: multiple_correct_key → award +4 to everyone who marked ANY correct option; all_options_correct → +4 to all who attempted; none_correct/dropped → +4 to ALL candidates regardless of attempt. These are verbatim NTA rules from both the NEET 2026 and JEE Main 2026 bulletins, and they require re-grading the entire cohort from stored raw responses.
 * PUT A BUBBLED SET-CODE FIELD ON EVERY SHEET and model per-set keys. Addmen processes 'Multiple test sets (A/B/C/D) … simultaneously' and flags a 'mismatched test paper set' at read time; Verificare has a dedicated Set Entity with per-set keys AND per-set right/wrong scores. Data model: `question_set (code, exam_id)` + `set_question_map (set_code, sheet_question_ordinal → canonical question_id)`, so shuffled sets map onto one canonical question bank and analytics aggregate correctly. Flag at read time: blank set code, multiple-marked set code, or a set code with no key loaded.
 * ADD A WRONG-KEY DETECTOR as a cheap post-grade heuristic. Verificare ships this as an AI feature; you can approximate it well: after a grading run, surface any question with (i) near-zero correct-rate across the whole cohort, or (ii) a correct-rate that collapses relative to its difficulty index, or (iii) an unusually high multi-mark rate. Addmen's advanced module already computes 'difficulty index, discrimination index, candidate response distribution, distractor analysis' per question — compute these from your own per-bubble table and use them as the outlier signal.
 * RETAIN THE ORIGINAL SHEET IMAGE AND BUBBLE CROPS. Both Addmen and Remark surface the original image inside every correction dialog ('it also shows the image of the original sheet to make it easy to compare'). On mobile this is cheap and it is the difference between a teacher trusting a re-grade and arguing with it. Store sheet-level image + per-question crop refs alongside the raw read row; keep the layout/geometry version used at read time so crops can be regenerated.
 * SUPPORT 'N-OF-M' SECTIONS. Model `section.max_counted` (questions counted = first N valid responses in serial order, extras ignored with no penalty) — this is NEET/JEE Main Section II behaviour and Addmen's documented 'answer 10 out of 15' logic. Without it you will mis-grade any NEET-pattern test where a student fills 6 of 5 required.
 * DESIGN THE INTEGER GRID WITH RIGHT-ALIGNED DIGITS AND EXPLICIT LEADING-ZERO SEMANTICS. Two digit columns (00–99) covers JEE Main (answers 'rounded off to the nearest integer') and most JEE Advanced integer items; make column count per-question configurable in the layout ('one-digit, two-digit or more digit blocks'). Resolve '03' vs '3' at the mapping layer as Addmen warns. Reuse the same digit-column widget and reader for the roll-number field, and apply Addmen's rule that blank columns are ignored but a filled '0' is a value — then validate the roll number against the enrolled ID list and flag 'Blank ID, Duplicate ID, Invalid Length, Invalid ID not in list, Multiple marked column'.
 * BUILD A 4-TYPE QUESTION CATALOGUE, NOT 1. (1) SINGLE_CORRECT, 4 options; (2) MULTI_CORRECT, 4 options, N-valid; (3) INTEGER_DIGITS, k columns × 10 digits; (4) MATRIX, r rows × c columns (one mark per row, partial or all-or-nothing scoring). Also allow a MATCH_LIST_REDUCTION type (list-match collapsed to an ordinary 4-option single-correct item, as JEE Advanced 2026 actually does) so one sheet can mix all of them — Addmen's IIT-pattern sheets do exactly this.
 * DESIGN BUBBLE GEOMETRY FOR DETECTION FIRST: ~40–50 px equivalent bubble (≈4.5–5.5 mm at 300 dpi), thin outlines, light/small option labels so they can never be thresholded as marks, and strict minimum inter-bubble gaps ('bubbles touching each others are defective sheets'). Print the bubble outline in a dropped-out colour or keep it very light if you ever scan in greyscale, since large dark labels 'could be falsely detected as filled marks on black-and-white sheets'. Target ≥150 dpi capture (Addmen: 100 dpi floor for OMR, 150 dpi for barcode/ICR) and design registration/timing marks to tolerate the skew your auto-alignment step corrects.
 * IMPLEMENT THREE READING MODES mirroring Addmen — Auto (skip and quarantine with a filename prefix), Alert (prompt per exception at read time), Manual (stop on every sheet) — plus a post-read editor that sorts by issue type and shows the sheet image. On a phone this maps to: background capture queue → exception inbox → per-sheet tap-through review, which is far better UX than blocking the camera on each ambiguous sheet.
 * VERSION EVERYTHING THAT AFFECTS A SCORE. Each `scoring_run` row records (answer_key_version_id, scoring_rule_snapshot, sheet_layout_version, threshold_param_set_id). This gives you a free audit trail, lets you reproduce any historical marksheet exactly, and makes the 'curve a test / throw out questions / change correct answers and regrade' workflow a safe insert rather than a destructive update. Addmen gates editing behind passwords and logs data-editing activity to SQL in its professional edition — do the same from day one.

===== RESEARCH (agent a27cc04c) =====
SUMMARY: Production mobile scanners converge on one architecture: a low-resolution live analysis stream that runs page-boundary detection + no-reference quality gates every frame, a hysteresis/consensus mechanism that requires several consecutive agreeing frames before auto-capture, and a separate full-resolution still capture (increasingly a short YUV burst with sharpest-frame selection). No shipping SDK exposes programmatic control over ML Kit's Document Scanner (verified: only gallery import, page limit, and scanner mode), so an OMR-grade capture loop must be custom-built — and the open-source record (WeScan, LiveEdgeDetection, OMRChecker) plus Scanbot/Dynamsoft/BlinkID documentation gives concrete, copyable threshold values for every gate. The dominant risk is capture, not detection: OMRChecker reports ~100% accuracy on flat scans vs ~90% on phone photos, and the largest published OMR study (6,029 sheets, 564,040 answers) attributes residual errors overwhelmingly to mark-quality (faint/partial/over-large/erased marks, student annotations, sheet folding) rather than to algorithm limits. The single most important Android platform constraint is that binding ImageCapture caps ImageAnalysis at PREVIEW size (default 640x480), which forces a detect-low-res / capture-high-res split; a 1080p preview frame yields only ~21 px per 4.2 mm bubble, so bubbles must be read from the captured still, never from the analysis stream.

 - CLASSICAL EDGE PIPELINE CANONICAL FORM (Scanbot engineering blog 'How to detect document edges in OpenCV'): grayscale -> GaussianBlur(5,5,0) -> Otsu (cv2.threshold(...,0,255,THRESH_BINARY+THRESH_OTSU)) -> Canny(binary, 50, 150) -> findContours(RETR_EXTERNAL, CHAIN_APPROX_SIMPLE) -> sort by contourArea descending, keep TOP 5 -> arcLength(contour, True) -> approxPolyDP(contour, 0.02 * peri, True) -> accept the first contour whose approximation is EXACTLY 4 points. No Hough transform anywhere; the blog explicitly notes the classical approach 'doesn't work well on bright surfaces' and points to ML detection for noise, low contrast, shadows and clutter.

 - BURST / SHARPEST-FRAME LATENCY NUMBERS: on camera2 (StackOverflow 29265126, Nexus 5 measurements) JPEG output stalls 243 ms PER FRAME, RAW_SENSOR 200 ms, while YUV_420_888 has 0 ms stall and minimum frame duration at full resolution is 33 ms (~30fps) — so a frame-selection burst must read an ImageReader in YUV, not JPEG, and should disable EDGE_MODE / noise reduction / aberration correction and lock AE/AF for speed. Google's HDR+ (Hasinoff et al., SIGGRAPH Asia 2016) shows the ceiling for full burst fusion: FFT-based alignment plus a hybrid 2D/3D Wiener merge, no exposure bracketing, constant low exposure to protect highlights — and it still takes 4 SECONDS ON DEVICE for a 12 Mpix image (Camera2 + Halide).  - BLUR METRIC AND THRESHOLD REALITY: the de-facto standard is variance of the Laplacian, cv2.Laplacian(gray, cv2.CV_64F).var() (PyImageSearch 'Blur detection with OpenCV'), credited to Pech-Pacheco et al. 2000 and chosen from Pertuz et al. 2013's survey of ~36 focus operators; PyImageSearch's default threshold is 100.0 but the author is explicit that 'this value is quite subjective to the contents of the image(s)' and must be tuned per dataset — demo scores span 64.25 / 83.17 (blurry) to 1004.14 (sharp), i.e. orders of magnitude. FFT-based sharpness was rejected for ambiguous high/low-frequency cutoffs. A published mobile-document study ('Automatic blur detection in mobile captured document images', IEEE 6707602) tested on 4000+ mobile captures and reports 'optimum parameter values' for motion blur vs defocus, using an edge-model blur-level measure (transition/peak/line edge models) rather than raw Laplacian variance.
 - OMR ACCURACY BASELINES (the numbers this project must beat): OMRChecker (github.com/Udayraj123/OMRChecker, MIT, ~1.1k stars) README: 'nearly 100% accurate on good quality document scans; and about 90% accurate on mobile images', 200+ OMRs/min, min supported resolution badge 640x480, and its --autoAlign preprocessor was REMOVED 'due to low performance on a generic OMR sheet' (evidence that generic keypoint auto-alignment is the wrong tool — use dedicated registration marks). A web-camera OMR system using Canny edge detection is cited at 94% accuracy.
 - BEST PUBLISHED LARGE-SCALE OMR ERROR BREAKDOWN (Hernandez-Mier et al., 'Unsupervised Optical Mark Recognition on Answer Sheets for Massive Printed Multiple-Choice Tests', J. Imaging 11(9):308, Sept 2025; 6,029 sheets, 564,040 answers, 2,256,160 circles from 44 campuses): 99.95% of individual answers correct (424 errors), 96.15% of exams error-free (5,797/6,029), roll-number/ID section 99.50% (29 errors), 1.05 s/sheet on an i7-4770. Circle detection 99.26% vs 80.64% for a Circle Hough Transform baseline — and on MARKED circles specifically, 97.45% vs 31.28%. Weakest class: multiple-marked items (>80%). 166 exams had exactly 1 error. The authors attribute most errors to 'the assessed student not following the instructions' on marking, and enumerate the hard cases: handwritten annotations over marks/rectangles, sheet folding, marks exceeding the circle boundary, blurry marks, faint/incomplete/partial diagonal fills, wrong scan orientation, digitization artifacts, and ERASURE SMUDGES affecting adjacent marks. Their pipeline is the recommended reference: resize to fixed 1670x1290 -> grayscale -> illumination correction by morphological opening with a 25x25 kernel -> Otsu -> contour-detect two reference rectangles -> homography -> HSV S/V analysis + adaptive threshold -> circle ordering -> decision by combined binary pixel-count AND grayscale-mean test against a clean-sheet reference, with 3 fallback rectangle-finders and 4 fallback circle-finders (main algorithm sufficed on 97–98% of sheets).
 - MARK-STATE TAXONOMY IS A REAL CLASSIFIER PROBLEM, NOT A THRESHOLD: Afifi & Hussain (arXiv:1711.00972) classify each box as 'confirmed, crossed out, or blank' — cancelled answers look like marks to any pixel-count threshold, and the paper's motivation is that rigid OMR protocols produce 'erroneous evaluations'. Published failure figures also call out 'marks exceeding the space of the circle' and 'different tonalities' of ink as distinct error classes.
 - FIDUCIAL-LOSS AND SKEW ARE NAMED OMR FAILURE MODES IN THE SMARTPHONE LITERATURE: Hafeez et al., 'An Enhanced Fault Tolerance Algorithm for Optical Mark Recognition Using Smartphone Cameras' (IEEE 10658966, 2024) illustrates a missing fiducial marker as its headline error case; 'Fault Tolerant Optical Mark Recognition' (2022) detects skew via a CENTRAL BOLD BAR on the sheet — i.e. put the timing/registration marks mid-sheet, not only in corners, if you control the layout.
 - DOCUMENT-CAPTURE ERROR TAXONOMY WITH NUMBERS (picturetext.org engineering blog on mobile camera OCR errors — vendor source, treat numbers as indicative): phone-camera document photos carry a 3–8x higher character error rate than flatbed scans at equal resolution. Barrel distortion: generic wide-angle k1 = −0.15 to −0.25 removes 70–85% of it, baselines return to within ±1.5 deg, CER −15–25%. Perspective: at 5–35 deg off-perpendicular, character width varied up to 34%; four-corner homography cut residual to under 2%, CER −20–35%. Depth-of-field: f/1.8–2.4 gives only 5–10 mm DoF at 20–40 cm, producing sharp-centre/soft-edge frames; the fix is re-shooting flat from 50–60 cm overhead. Motion blur: indoor shutters of 1/30–1/60 s with 8–12 Hz hand tremor of 0.5–2 mm amplitude produce 1–8 px of sensor displacement; Wiener deconvolution recovers up to ~12 px, above ~15 px RE-CAPTURE. Flash glare: a 40–120 px fully-saturated (255,255,255) zone; fix is oblique lighting at 30–45 deg, or threshold at intensity 245 and histogram-stretch. Stated general protocol: 25–40 cm distance, sensor parallel to page, diffuse light, FLASH OFF.
 - PEN VS PENCIL (vendor consensus across Addmen Group, omrsheet.com, Yoctel): blue or black BALLPOINT gives 'strong, quick-dry marks that scanners detect reliably'; gel and fountain pens are discouraged for slow drying, bleed-through and smudges that create ghost marks; pencil is acceptable at HB/2B or darker but 'complicates scanner settings' and risks faint marks; JEE Main policy is black ballpoint only. Practically the reader detects a dark patch and cannot distinguish instrument — DARKNESS, not ink type, is the signal — so a captured sheet must be thresholded per-sheet, not globally.
 - GUIDANCE UX HAS ONE REAL PUBLISHED EVALUATION: SmartDCap ('Semi-automatic capture of higher quality document images from a smartphone', IUI) gives real-time framing and sharpness feedback and combines metrics into a single score shown to the user WITH AUDIO FEEDBACK. In a 12-subject within-subject study against the stock Android ICS camera, SmartDCap images were 'sharper and better framed on average' — but subjects 'were conflicted about aligning a document with the green rectangles' and rated the alignment task moderately difficult, while still rating the app as easy to use as the stock camera. Related evidence that real-time beats static guidance: CHI 2015 'Real-time Guidance Camera Interface' and CHI 2019 'PicMe'. For scanning specifically, Scanbot's blogs describe the standard cue set ('move closer', 'adjust angle', 'improve the lighting', 'hold still') but publish NO measured effect — no published study measures distance/angle prompts on OMR capture quality.
 - GLARE DETECTION HEURISTICS THAT ARE ACTUALLY USED: the lighting/evalglare convention is 'pixels of luminance x-times larger than the average luminance of a pre-defined zone' (multiplicative, region-relative — robust to overall exposure, unlike a fixed cutoff); a perception study puts informative luminance at up to ~the 80th percentile of the histogram; light-field specular work parameterises the highlight threshold 'hthres' freely in [0,255] as 'the lowest intensity of specular pixels'; most physics-based methods assume the specular colour approximates the ILLUMINANT colour (near-white), which is why a near-white + low-saturation test on the VALUE channel works for flash on paper. For training data, SHDocs (OpenReview) is a purpose-built real-world document specular-highlight dataset.

RECS:
 * ARCHITECTURE: do NOT use ML Kit Document Scanner for capture (verified closed: only gallery/pageLimit/mode controls, no camera/threshold/overlay hooks). Build the loop on CameraX with THREE use cases: Preview + ImageAnalysis(STRATEGY_KEEP_ONLY_LATEST, default 640x480 or 1280x720) + ImageCapture(CAPTURE_MODE_ZERO_SHUTTER_LAG or MAXIMIZE_RESOLUTION). Bind Preview+ImageAnalysis FIRST and add ImageCapture in a second bindToLifecycle() call, because binding ImageCapture caps ImageAnalysis at PREVIEW size (~1024x768 on Level-3 devices). Detect on the cheap stream, grade from the full-res still.
 * DETECTION ALGORITHM (per analysis frame, in Kotlin via OpenCV 4.x or a small JNI/native module): downscale to ~480px on the long side -> grayscale -> GaussianBlur(5,5) -> THRESH_TRUNC at 150 to normalise paper to near-white -> Canny(85,185) -> THRESH_TOZERO at 155 to kill weak edges -> morphologyEx(MORPH_CLOSE, 10x10, 1 iteration) -> findContours(RETR_LIST, CHAIN_APPROX_SIMPLE) -> convexHull -> sort by contourArea, keep top 10 -> arcLength -> approxPolyDP(0.02*perimeter) -> first 4-point hull wins -> order corners by min(x+y)/max(x+y)/min(y−x)/max(y−x). This is LiveEdgeDetection's ScanUtils.detectLargestQuadrilateral verbatim and it is fast enough at 640x480 to run every frame inside the 32ms/30fps CameraX budget. Skip Hough entirely — no shipping scanner uses it for page finding.
 * PREFER MARK-BASED REGISTRATION OVER EDGE-FINDING FOR THE FINAL WARP. You control the printed sheet, so use the corner fiducials + timing track: template-match each fiducial with cv2.matchTemplate(..., TM_CCOEFF_NORMED) restricted to four quadrants, accepting a quadrant only if its peak >= 0.3 AND within 0.41 of the global best peak, sweeping marker scale 35–100% in 10 steps (these are OMRChecker's CropOnMarkers.py defaults, proven on real Indian-style sheets). Use the contour quad for the LIVE overlay and coarse gating, and the fiducials for the authoritative homography at grading time. Keep a mid-sheet timing bar as a second, skew-only reference (per the Fault Tolerant OMR 2022 design) because corner fiducials are the single named failure mode in the smartphone-OMR literature (missing fiducial marker, Hafeez 2024).
 * HYSTERESIS / AUTO-CAPTURE STATE MACHINE: maintain a rolling queue of 8 detected quads with a 3-quad minimum; count a 'stable pass' only when the new quad's four corners are within 6 px of the running consensus quad, and fire auto-capture after 35 consecutive stable passes; reset on 3 consecutive misses (these are WeScan's RectangleFeaturesFunnel constants: matchingThreshold 40px, autoScanMatchingThreshold 6.0px, autoScanThreshold 35, maxNumberOfRectangles 8, minNumberOfRectangles 3, noRectangleThreshold 3). Expose the stability as a progress ring like Scanbot's polygonAutoSnappingProgressStrokeColor, and expose the sensitivity as a single [0..1] knob mapping to a 0.66-default ~1s timeout (Scanbot's DocumentAutoSnappingController contract). ALWAYS keep a manual shutter that bypasses the gate, and always allow corner re-edit afterwards.
 * FIVE PARALLEL LIVE GATES with the vocabulary Scanbot ships (OK / OK_BUT_TOO_SMALL / OK_BUT_BAD_ANGLES / OK_BUT_TOO_DARK / ERROR_TOO_DARK / ERROR_TOO_NOISY / ERROR_PARTIALLY_VISIBLE), each mapped to one hint: (1) AREA: quad between 0.20x and 0.95x of preview area; <0.25x -> 'move closer'; >0.75x or width/height ratio >0.9 -> 'move away'; touching within 50px of frame edge -> 'move away'. (2) ANGLE: max cosine of the four interior angles < 0.085 (all corners within ~87–93 deg, LiveEdgeDetection's threshold; Dynamsoft enforces the equivalent 70–110 deg CornerAngleRange). (3) BLUR. (4) EXPOSURE. (5) GLARE. Only AREA_+ANGLE_+BLUR_+EXPOSURE all green advances the hysteresis counter.
 * BLUR GATE: compute variance of the Laplacian (cv2.Laplacian(gray, CV_64F).var()) on the Y plane of the analysis frame, DOWNSCALED TO A FIXED SIZE (e.g. 320px long side) so the score is scale-comparable across devices, and compute it INSIDE THE DETECTED QUAD ONLY, not the whole frame. Calibrate the threshold empirically on ~200 of your own phone captures rather than copying PyImageSearch's 100.0 — that number is explicitly dataset-subjective and scores span 64 to 1004 across content. Ship three strictness presets (Strict/Normal/Relaxed) exactly as BlinkID's blurStrictnessLevel does, and default to Normal. Cheaper and more robust than absolute variance: track the metric ACROSS frames and fire only when the current frame is at or above the rolling 75th percentile — this is what Dynamsoft's enableFrameVerification ('clarity detection plus cross-filtering') actually does, and a relative test removes the calibration problem.
 * EXPOSURE GATE: mean Y-plane luminance of the quad in a sane band (roughly 60–200 on the 0–255 Y plane, mid-point ~110–140 for matte uncoated paper), plus reject if more than a small fraction of quad pixels are clipped at 245+. Use a REGION-RELATIVE glare test rather than a fixed cutoff: flag a specular hotspot when a contiguous region's luminance exceeds k× the mean luminance of its surrounding zone (the evalglare convention), combined with near-zero saturation in HSV — this survives torch-on/torch-off and ambient changes where an absolute threshold does not. Offer THREE levels like BlinkID (glareStrictnessLevel) and default the glare filter ON.
 * RESOLUTION GATE (the >=40 px-per-bubble requirement, derived arithmetic — verify against your own printed layout): an A4 sheet is 210 mm across the short side. At a typical Indian-sheet bubble diameter of ~4.2 mm, 40 px per bubble needs >=9.5 px/mm, i.e. >=2,000 px across the sheet's short side in the CAPTURED STILL. Two consequences: (a) a 1080p preview/analysis frame is NOT enough (1080/210 = 5.1 px/mm -> ~21 px per bubble), so bubbles must be read from the ImageCapture still, never from the analysis stream; (b) enforce the check live as a fraction of frame width: quadShortSidePx / analysisFrameWidthPx must be >= (2000 / stillWidthPx). At 640px-wide analysis and a 4000px-wide 12MP still that is a 6.25x factor, so require the quad's short side >= ~320 analysis px — the same 'move closer' gate as the area rule, but expressed so it cannot be satisfied by zooming in on only part of the sheet. Print the sheet with bubble pitch no smaller than ~5 mm to keep this comfortable.
 * CAPTURE POLICY — take a SHORT YUV BURST, not one frame, and select the sharpest: on trigger, grab 3–5 consecutive YUV_420_888 frames via an ImageReader (0 ms stall per frame on camera2; JPEG stalls ~243 ms/frame on the reference Nexus 5 measurement, so never burst in JPEG), score each with the same Laplacian-variance metric, and keep the best-scoring frame that also has the quad in the same position. Cap it at ~5 frames; full burst fusion such as HDR+ takes 4 s on-device for 12 Mpix, which is unusable inside an interactive loop, whereas single-metric frame selection is what Dynamsoft ships by default (enableFrameVerification, minVerifiedFramesForAutoCapture 2 of 1–5). Re-run the five gates on the SELECTED frame before accepting it — this is the fix for LiveEdgeDetection's bug where geometry is validated on a preview frame but a fresh, unvalidated still is saved. Lock AE/AF before the burst and disable EDGE_MODE / noise reduction / aberration correction for burst speed.
 * LIGHTING / TORCH POLICY for glossy ballpoint on matte paper: default TORCH OFF; ambient diffuse light wins. Enable torch only as an explicit fallback when mean quad luminance stays below the exposure band for >1.5 s, and when the torch is on, REQUIRE the user to tilt the phone (oblique 30–45 deg to the page) so the specular cone misses the lens — a near-perpendicular flash at close range creates a 40–120 px fully-saturated zone that destroys any bubble under it. Instruct blue/black BALLPOINT and discourage gel pens (smudge, bleed-through, ghost marks); pencil HB/2B is readable but expect fainter marks, so if your institute allows pencil, lower the mark-decision threshold for those batches. Warn on hand shadows: they are the mirror of glare and should trip the same region-relative luminance-variance test (Scanbot's ERROR_TOO_NOISY).
 * GRADING-TIME MITIGATIONS THAT MAP TO EACH CAPTURE FAILURE (from the J. Imaging 2025 6,029-sheet study): faint/partial/diagonal fills and erasure smudges -> decide each bubble by a COMBINED binary pixel-count AND grayscale-mean test against a clean-sheet reference rather than a single coverage ratio; marks exceeding the circle -> use a Circle-Hough-free contour/roi approach (CHT scored only 31.28% on marked circles vs 97.45% for the reference method); student annotations over marks -> classify mark state (confirmed / crossed-out / blank, arXiv:1711.00972) and route ambiguous states to a human review queue instead of guessing; uneven illumination -> illumination correction by morphological opening with a 25x25 kernel BEFORE Otsu, then adaptive threshold per bubble region; sheet folded / not flat -> detect at capture via the depth-of-field gate (sharp centre, soft edges) and prompt re-capture rather than trying to read it.
 * UX CUES, in priority order, all driven off the gates above and all colour-coded like LiveEdgeDetection: 'move closer' (area < 0.25x preview), 'move away' (area > 0.75x or touching frame edge), 'adjust angle / hold flat' (max-cosine >= 0.085 or side-edge spread > 100px), 'hold still' (blur gate failing, shown with a filling progress ring as stability accumulates), 'too dark / more light' (exposure), 'glare — tilt the phone' (specular), and 'plain darker background helps' (LiveEdgeDetection notes detection works best on a dark backdrop). Keep the overlay quad animated and smoothed (WeScan's tie-break prefers the candidate nearest the currently displayed quad, which suppresses jitter), draw it green only when ALL gates pass, and add a single audio cue on capture as SmartDCap does. Budget for the SmartDCap finding that some users find rectangle-alignment confusing: pair the free-form quad overlay with a fixed A4-aspect finder frame so users have an unambiguous target to fill.
 * AVOID re-implementing generic alignment: OMRChecker removed its own --autoAlign preprocessor 'due to low performance on a generic OMR sheet' — since you print the sheet, fiducial template matching (CropOnMarkers) is both cheaper and more reliable than feature-based auto-alignment. Keep a --setLayout-style layout iteration tool so template.json (or its Kotlin equivalent) can be tuned against real captures before an exam.
